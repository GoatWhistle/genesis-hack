# Сайт RSOCKET — план

Составлено 5 сентября 2026 по актуальному коду (`53f36f0`): решение переписано на движок правил
(`app/config/rules/base.yml` + профили контрактов), HTTP-сервис `POST /build`, Docker.

Сайт — не «дока с лендингом». Это **витрина, которая показывает, как данные проходят через
инструмент**, и одновременно рабочая консоль к настоящему API. Жюри должно за четыре минуты
понять и поверить.

---

## 0. Рамки

- **Решение кейса не трогаем.** Ни `app/`, ни `bin/`, ни `spec/`, ни `docs/openapi.yaml`.
  Сайт только читает: `examples/`, `app/config/rules/`, `docs/http-api.md`,
  `docs/openapi.yaml` — и вызывает готовый HTTP API. Если для фичи сайта нужна правка
  бэкенда — фича делается эвристикой на стороне сайта или не делается.
- **Сайт живёт в этом репозитории, в `web/`.** Ни один Ruby-файл от него не зависит.
  `rubocop` и `rspec` его не видят и так — там нет `.rb`, конфиги не трогаем.
- **Вне `web/` появляется ровно две вещи**, и обе — новые файлы, не правки:
  `.github/workflows/` (GitHub читает его только из корня; оба workflow ограничены
  `paths: [web/**]`) и — по желанию — одна строка со ссылкой на сайт в README.
  Больше ничего в корне не меняется.
- **VPS, Caddy и домен есть.** Раздел 6 описывает только то, что докладываем поверх.
  Их `Dockerfile` и `compose.yaml` используются как есть, включая MinIO.

## 1. Что показываем — суть, которую сайт обязан донести

Главный тезис нового решения, которого не было в старом:

> **Инструмент не знает про платежи ничего в коде.** Всё знание — в двух YAML-файлах.
> `base.yml` — как чужие API называют одно и то же. `contract.yml` — под какой интерфейс
> собираем. Правка одной регулярки меняет результат немедленно, без перезапуска.

Три доказательства, которые сайт должен сделать осязаемыми:

| Доказательство | Чем подтверждается в коде | Как показать |
|---|---|---|
| Роли раздаются по правилам, а не по хардкоду | `report.roles.*.matched_rules`, `score`, `threshold`, veto | Табло кандидатов: каждая операция получает счёт по каждому архетипу, сработавшие правила подсвечены, veto зачёркивает |
| Правила живые | `PUT /rules/<ключ>`, перечитывание на каждый запрос | Правишь регулярку прямо на сайте → пересборка → роли разъехались иначе, diff |
| Не привязан к одному контракту | `plain_client` рядом с `space_payments`, `other_contract_spec.rb` | Одно описание → два класса рядом, синхронная прокрутка, соответствующие методы подсвечены |

Плюс честность: `warnings` — не сноска, а полноправный элемент интерфейса. Инструмент говорит
«не понял» — сайт показывает это так же заметно, как и «понял».

## 2. Страницы

### `/` — Главная

Не лендинг с тремя карточками преимуществ. Один экран — одна мысль, длинная прокрутка.

1. **Заголовок + живой мини-конвейер.** Прямо в первом экране крутится настоящий разбор
   NovaPay: слева операции описания, в центре они разбегаются по ролям, справа появляется
   код. Не видео — настоящий рендер из запечённого JSON, с анимацией по шагам. Кнопка
   «разобрать своё» ведёт в `/lab`.
2. **Проблема в одном кадре.** Четыре провайдера, одна и та же сумма 1500 ₽: `150000`,
   `1500.00`, `"1500.00"`, `1500`. Ползунок суммы — числа пересчитываются. Подпись: «Один
   из них отправит в сто раз больше, если перепутать».
3. **Два слоя правил.** Схема: `base.yml` (что бывает в платёжных API) ↔ `contract.yml`
   (под кого собираем). Интерактивно: наведение на архетип `creation` подсвечивает роли в
   обоих контрактах, которые на него ссылаются.
4. **Один вход — два выхода.** Split-view: `NovapayService` и `NovapayClient` из одного
   описания.
5. **Что инструмент не понял.** Реальные `warnings` с nordbank. Это позиция, а не оправдание.
6. **Как запустить.** Три способа: `curl`, `bin/rsocket build`, `docker compose up`. Копируемые.

### `/lab` — Разбор вживую (ядро сайта)

Полный проход данных через инструмент, по шагам, с возможностью остановиться на любом.

**Вход:** выбрать одно из четырёх описаний, вставить своё YAML/JSON, или перетащить файл.
Редактор — CodeMirror 6 с подсветкой YAML.

**Шаги конвейера** (горизонтальная лента этапов, каждый раскрывается):

1. **Разбор** — список операций: метод, путь, `operationId`, теги. Клик → фрагмент YAML.
2. **Раздача ролей** — центральная сцена. Для каждой роли контракта по порядку
   (`create_request → fetch_status → …`): все свободные операции получают счёт. Столбики
   счёта растут по мере срабатывания правил; правило появляется подписью
   (`operation_id =~ /\A(create|make|…)/ → +6`); veto перечёркивает кандидата красной
   чертой; порог — горизонтальная линия; победитель уходит из пула. Рядом — объяснение
   словами из `why`, если роль осталась заглушкой.
3. **Статусы** — слова провайдера прилетают в три группы (`settled` / `failed` /
   `pending`) через регулярки, потом группы переводятся в статусы контракта.
   Наведение на слово → какая регулярка его поймала.
4. **Сумма, ограничения, авторизация, webhook** — четыре компактных блока:
   множитель и почему; `conditions` с `source` («minimum у поля amount в схеме
   запроса»); выбранная схема авторизации и альтернативы; подпись webhook.
5. **Код** — сгенерированные файлы с вкладками. **Каждая строка знает, откуда она:**
   наведение на `MIN_AMOUNT = 1000` подсвечивает ограничение на шаге 4 и поле в YAML на
   шаге 1. Наведение на `def create_request` — роль на шаге 2 и её правила.
6. **Предупреждения** — отдельной колонкой справа, всегда видны.

**Правая панель:** переключатель контракта (`space_payments` / `plain_client`) — сцена
перестраивается, код меняется, роли остаются теми же операциями. Это и есть доказательство.

**Ссылка на прогон.** Состояние (провайдер, контракт, правки правил) кодируется в URL —
можно отправить жюри ссылку на конкретный разбор.

**Два режима работы:**
- *Запечённый* — четыре описания собраны на этапе сборки сайта, JSON лежит в бандле.
  Работает без бэкенда. Показ никогда не сломается из-за упавшего сервера.
- *Живой* — своё описание и правки правил уходят в настоящий `POST /build`. Индикатор
  режима видим.

### `/rules` — Правила

Браузер хранилища правил поверх `GET /rules` и `GET /rules/<ключ>`.

- Дерево: `base.yml`, `contracts/space_payments/*`, `contracts/plain_client/*`.
- `base.yml` не как текст, а как **структура**: архетипы с их правилами и veto,
  группы статусов, семантика ошибок, паттерны полей. Каждая регулярка — с полем
  «проверить»: вводишь `cancelPayout` → видно, какие правила совпали и какой veto сработал.
- **Песочница правил:** изменил вес или регулярку → «пересобрать все четыре» → таблица
  ролей до/после с подсветкой изменений. Не пишет в хранилище, пока не нажал «сохранить»
  (`PUT`). В запечённом режиме — только просмотр с честной подписью.
- Шаблоны `.erb` — с подсветкой и подписями, какие переменные откуда.

### `/providers` — Четыре описания

Сравнительная таблица по строкам: имя операции создания, единицы суммы, авторизация,
статусы, webhook, что не распознано. Сделано, чтобы было видно: описания **нарочно
непохожие**, и инструмент справился со всеми.

Каждый провайдер раскрывается: его YAML, его отчёт, его код, его `INTEGRATION.md`
(рендер markdown), `fixtures.json`.

### `/docs` — Документация

- **CLI** — не список флагов, а **воспроизводимая запись терминала**: каждая команда
  показана как настоящий вывод (собранный из JSON, с анимацией набора, кнопка «повторить»).
  `build`, `serve`, `push`, `contracts`, `doctor`.
- **HTTP API** — из `docs/openapi.yaml`. Не Swagger UI по умолчанию, а своя разметка:
  ручка → запрос → ответ → ошибки, с кнопкой «выполнить» в живом режиме.
  Все примеры из `docs/http-api.md`.
- **Хранилища** — local / S3, переменные, `compose.yaml`.
- **Как добавить контракт** — пошагово, с реальным `plain_client` в качестве примера.
- **Как добавить правило** — «провайдер называет создание `dispatch` → одна строка в
  `base.yml`».

### `/architecture` — Как устроено

Схема портов и адаптеров из `app/boot.rb`: `SpecSource → Parser → Classifier → Analysis →
Renderer → Uploader`. Интерактивная: клик на узел → какие файлы, какой порт, чем
подменяется в тестах. Ниже — почему два слоя правил, почему veto, почему ничьи решаются
порядком объявления.

## 3. Идеи «сверх» — по убыванию отдачи

| # | Идея | Зачем | Цена |
|---|---|---|---|
| 1 | **Строка кода → её причина.** Наведение на любую строку сгенерированного файла подсвечивает правило и фрагмент YAML | Единственная вещь, которую жюри запомнит | средняя — карта «строка → источник» строится на сайте из `report` и шаблонов `.erb`, бэкенд не трогаем |
| 2 | **Песочница правил с diff до/после** | Живое доказательство, что решение — в правилах | низкая — бэкенд уже умеет |
| 3 | **Анимация раздачи ролей со счётом** | Показывает механику, а не результат | средняя |
| 4 | **Ползунок суммы × четыре провайдера** | История про ошибку в 100 раз — за пять секунд | низкая |
| 5 | **Split-view двух контрактов** с синхронной прокруткой | Аргумент против «генератор под один интерфейс» | низкая |
| 6 | **Ссылка на прогон** (состояние в URL) | Жюри открывает готовый разбор по ссылке | низкая |
| 7 | **Терминал с записью вывода CLI** | Дока, которую читают, а не пролистывают | средняя |
| 8 | **«Проверить регулярку»** у каждого правила | Понятно, что правила — не магия | низкая |
| 9 | **Загрузка своего описания в живом режиме** | Жюри может подсунуть своё | низкая (бэкенд готов), риск — CORS/лимиты |
| 10 | **Экспорт результата zip** | Практично | низкая |
| 11 | **Схема архитектуры с кликабельными узлами** | Оценивают документацию проекта | средняя |
| 12 | **История прогонов в localStorage** | Вернуться к разбору | низкая |

Идея 1 — только эвристикой на стороне сайта, бэкенд не трогаем: `def <роль>` → роль из
`report.roles`, константы `MIN_AMOUNT`/`MAX_AMOUNT`/`ALLOWED_CURRENCIES` → `conditions`
по полю `constant` из `contract.yml`, `STATUS_MAP` → `statuses`, заголовок авторизации →
`auth`. Шаблоны `.erb` читаем из `app/config/rules/` — в них видно, какая переменная
куда печатается, этого хватает для карты «строка → источник».

## 4. Дизайн — направление, не мудборд

Проверено через impeccable и ui-ux-pro-max. Их «дефолт» для dev-tool — slate + зелёный,
JetBrains Mono, тёмная тема. Это ровно то, что выглядит как сгенерированное. Отказ.

**Сцена.** Судья хакатона, вечер, аудитория с включённым светом, проектор. Смотрит с
шести метров, должен за четыре минуты понять, что происходит с данными.
→ **Светлая тема**: тёмные интерфейсы на проекторе при свете превращаются в серую кашу.
Не кремовая, не «бумажная» — белый с нулевой хромой, чернильный текст.

**Голос** тремя словами: точный, дотошный, прямолинейный. Физический объект — двуязычный
разговорник: две колонки, левая — чужой язык, правая — наш, между ними правило перевода.

**Цвет — полная палитра с ролями, а не декор.** Сайт про встречу двух сторон, и цвет
кодирует сторону всюду, во всех визуализациях:

| Роль | Что красит |
|---|---|
| Сторона провайдера — киноварь (OKLCH ~0.62 0.21 30) | операции, поля, статусы провайдера, YAML |
| Сторона контракта — ультрамарин (OKLCH ~0.48 0.20 265) | роли, методы, статусы контракта, код |
| Правило / мост — чернила | регулярки, счёт, порог |
| Veto / предупреждение — не третий яркий цвет, а чернила с перечёркиванием и знак | не размывать систему |

Ориентир, который можно назвать вслух: швейцарские двуязычные железнодорожные схемы —
чёрное на белом, один цвет на направление.

**Шрифты** — обязательно с полноценной кириллицей, сайт на русском:
- Текст и интерфейс: **Golos Text** (Paratype) или **Onest** — кириллица родная, не из
  списка приевшихся.
- Заголовки: тот же Golos в тяжёлом весе, или **Unbounded** для одного-двух акцентов.
  Не два похожих гротеска.
- Код: **Martian Mono** — кириллица есть, отличим от JetBrains/Fira.
Финальный выбор — на `impeccable init`, там же `DESIGN.md`.

**Запрещено** (из impeccable, дополнительно к здравому смыслу): цветные полосы слева у
карточек, градиентный текст, стекло, «большая цифра + подпись» как шаблон метрики, сетки
одинаковых карточек, мелкий капс-кикер над каждым разделом, `01 / 02 / 03` где нет
реальной последовательности, тёмная тема «потому что dev-tool», serif-italic-editorial.

**Движение.** Одна главная хореография — раздача ролей в `/lab`. Всё остальное сдержанно.
Easing — только ease-out (quart/expo), без bounce. `prefers-reduced-motion` — обязательно,
финальное состояние показывается сразу.

| Слой | Выбор | Почему |

## 6. Деплой и CD

Цель: `git push main` → через несколько минут сайт и бэкенд обновлены на своём домене.
Без ручных шагов.

### Топология — один VPS, один домен, один источник

```
rsocket.<домен>          → Caddy → статика сайта (dist/)
rsocket.<домен>/api/*    → Caddy → rsocket:9292 (их compose.yaml как есть)
                                   minio:9000, rules — внутренняя сеть, наружу не торчат
```

Бэкенд на проде — ровно их `compose.yaml`: MinIO как S3, разовый `rules` переносит
правила в бакет, `rsocket` читает их оттуда. Ничего в нём не меняем и не отключаем.
Полезный побочный эффект: если кто-то через `PUT /rules` испортит правила на показе —
`docker compose restart rules` возвращает их из репозитория.

Один origin — нет CORS, нет прокси в Vite для прода, одна TLS-выдача. Caddy получает
сертификат сам (Let's Encrypt), обновляет сам.

Caddy — граница безопасности: у бэкенда нет ни авторизации, ни лимитов (по его же доке).
В Caddyfile: лимит тела 8 МБ, rate limit на `/api/build`, `PUT /api/rules/*` — только с
токеном в заголовке (или вовсе закрыт снаружи; песочница правил на сайте тогда работает
в режиме «показать diff, не сохранять»). Решить до показа.

### Хостинг — что уже есть и что докладываем

Есть: VPS, Caddy, домен. Докладываем: блок в существующий Caddyfile (сайт-хост + `/api/*`
→ `rsocket:9292`), `compose.prod.yaml` в `web/infra/`, который **включает** их
`compose.yaml` как есть (`include:`) и добавляет только сеть с Caddy. Их `Dockerfile` и
`compose.yaml` не редактируем.

### Пайплайн GitHub Actions

Workflow один — `deploy.yml`, с `paths: [web/**]`: пуш в Ruby-часть сайт не
пересобирает. Отдельного CI нет намеренно: проверять сайт в отрыве от выкладки
незачем, а два пайплайна на один каталог — лишняя точка расхождения. Всё, что
проверялось бы в CI, идёт первым шагом самой выкладки, поэтому сломанное на
прод не уедет.

Шаги (этапы названы по-английски, комментариев в файле нет):

1. **Build** — `pnpm install --frozen-lockfile`, `typecheck`, `lint` (он же
   проверяет запрет комментариев), `build`, `smoke`.
2. **Authorize** — ключ и `ssh-keyscan`; проверка хоста остаётся включённой.
3. **Upload** — `rsync` в `/srv/rsocket/releases/<sha>`, переключение симлинка
   `current` одним `mv -T`. Путь предыдущего выпуска записывается ДО
   переключения, хранится пять последних.
4. **Restart services** — `docker compose -p rsocket -f web/infra/compose.prod.yaml
   up -d --build --wait` на сервере.
5. **Smoke test and rollback** — `curl` по `/` и `/api/health`; если не
   отвечает, симлинк возвращается на предыдущий выпуск, а шаг падает.

Секреты: `SSH_KEY`, `SSH_HOST`, `SSH_USER`; переменная `SITE_URL`.
4. Smoke: `curl /api/health` и `curl /` → 200, иначе откат на предыдущий образ
   (`:prev` тег) и красный статус.

Превью для PR: если возьмём Cloudflare Pages для статики — бесплатно; на VPS — не делаем.

Одна дорогая хореография запоминается, десяток мелких — раздражает. Поэтому:

- [x] **Главная сцена — раздача ролей.** Операции провайдера по очереди
      примеряются к ролям: растёт столбик счёта, всплывают сработавшие правила,
      veto перечёркивает кандидата, победитель уходит к роли и исчезает из пула.
      Управляемо: «повторить», пауза, перемотка по шагам.
- [x] **Переключение контракта.** Роли и код
      перестраиваются с сохранением позиций: видно, что операции остались те же,
      а изменилась только правая сторона. Это ровно то доказательство, ради
      которого сделан второй контракт.
- [x] **Числа пересчитываются.** Ползунок суммы:
      `150000` доезжает до нового значения, а не подменяется мгновенно.
- [x] **Связь строки кода с её источником** — не мигание, а спокойная

- [x] **Ограничения движения.** Только ease-out (`--ease-out-quart`,

      свойствах, вызывающих перекладку (`width`, `height`, `top`) — только

      показывает, как оно сложилось, но никогда не решает, показывать ли его.

### Архитектура фронтенда

Сейчас плоские каталоги-мусорки: в `src/home/` и `src/lab/` по 16 файлов вперемешку
— компоненты, хуки, чистая логика и CSS в одной куче. `src/components/` пуст.
Имя `src/docs/` спорит с корневым `docs/` репозитория. Найти нужное можно только
перебором.

Перекладываем **после того, как агенты допишут страницы** — иначе переезд
столкнётся с их правками. Целевой вид:

```
src/
├── main.tsx
├── shared/                    общее для всех страниц
│   ├── api/                   клиент, запечённые прогоны, правила, типы
│   ├── model/                 чистая логика без React: provenance, match, compare
│   ├── ui/                    переиспользуемые: CodeBlock, Markdown, Terminal,
│   │                          FileTabs, Chip, Notice, Switch
│   ├── lib/                   хуки общего назначения: useHighlight, useRoute
│   └── design/                токены, примитивы, знак проекта
├── layout/                    оболочка: App, SiteHeader, SiteFooter, routes
└── screens/                   по экрану на каталог, внутри — своя раскладка
    ├── home/{ui,model}/
    ├── lab/{ui,model}/
    ├── rules/{ui,model}/
    ├── providers/{ui,model}/
    ├── docs/{ui,model}/
    └── architecture/{ui,model}/
```

Правила, по которым раскладываем:

- **Экран — это каталог, а не файл.** Внутри `ui/` (React) и `model/` (чистые
  функции и данные). Проверяемое отделено от рисуемого.
- **`shared/` только для того, что нужно двум и более экранам.** Утащить туда
  «на всякий случай» — так же плохо, как дублировать.
- **Дубликаты свести.** Подсветка кода, загрузка прогонов, рендер markdown,
  вкладки файлов сейчас написаны по-разному в разных каталогах — оставить по
  одной реализации в `shared/`.
- **Экран не импортирует из чужого экрана.** Понадобилось — значит, это
  `shared/`. Проверяется линтером (`no-restricted-imports`).
- **CSS рядом с тем, что он красит**, а не свалкой: общее — в `shared/design/`,
  частное — в каталоге своего экрана.
- Переезд делается одним заходом и проверяется `pnpm typecheck && pnpm lint &&
  pnpm build` плюс обходом всех шести страниц в браузере.

## 11. Финальные аудиты — обязательный этап перед сдачей

Замечание заказчика после первой сборки страниц: «сайт пиздец ИИ слоп».
Содержание к этому моменту верное — данные настоящие, механика показана честно, —
но форма всё ещё выдаёт происхождение: ровные сетки, предсказуемая типографика,
одинаковая плотность, украшательство вместо смысла.

Поэтому после того, как все страницы собраны, а архитектура разложена, идут
**два независимых аудита подряд**. Ни один нельзя пропустить, и оба делаются
до сдачи, а не «если останется время».

### Аудит 1 — impeccable

Прогнать по каждой из шести страниц:

```
/impeccable critique <страница>     разбор с оценкой по эвристикам
/impeccable audit <страница>        доступность, отзывчивость, производительность
/impeccable polish <страница>       довести найденное
```

Что проверяем прицельно — это ровно те места, где ИИ-происхождение видно:

- **Тест на слоп из самого скилла:** если по странице можно без сомнений сказать
  «это сделал ИИ» — она не прошла. Смотреть на: одинаковые карточки в сетке,
  мелкий капс-кикер над каждым разделом, нумерацию `01/02/03` там, где нет
  настоящей последовательности, «большую цифру с подписью» как шаблон метрики,
  градиентный текст, стекло, цветные полосы слева.
- **Реестр запретов** соблюдён без исключений.
- **Типографика:** шкала с шагом ≥1.25, длина строки 65–75 знаков,
  `text-wrap: balance` на заголовках, отсутствие двух похожих гротесков рядом.
- **Ритм:** секции обязаны отличаться плотностью и шириной. Одинаковый
  вертикальный отступ у всех блоков — главный признак шаблона.
- **Движение:** одна дорогая хореография вместо россыпи одинаковых «въездов
  снизу при прокрутке». Проверить, что нет уnifиcированного рефлекса.

### Аудит 2 — ui-ux-pro-max

После правок impeccable — второй проход другим взглядом:

```
python .../ui-ux-pro-max/scripts/search.py "<запрос>" --domain ux
python .../ui-ux-pro-max/scripts/search.py "<запрос>" --stack react
```

Прогнать по категориям приоритета скилла, с 1 по 10:

1. доступность: контраст, alt, клавиатура, aria;
2. цели нажатия ≥44×44 и отклик на действие;
3. производительность: вес бандла, ленивая загрузка, отсутствие сдвигов вёрстки;
4. соответствие стиля продукту;
5. отзывчивость: 375 / 768 / 1024 / 1440 без горизонтальной прокрутки;
6. типографика и цвет через семантические токены;
7. осмысленность анимации;
8. формы и обратная связь;
9. предсказуемая навигация;
10. читаемость данных и подписи.

Плюс сверить решения по палитре и шрифтам с их базой: наш выбор (светлая тема,
киноварь/ультрамарин, Golos Text + Martian Mono) должен пережить проверку или
быть осознанно защищён.

### Как принимаем

- Все находки уровня P0 и P1 закрыты, остальные — либо закрыты, либо записаны с
  причиной отказа.
- Финальный прогон: `pnpm typecheck && pnpm lint && pnpm build` зелёный,
  `node scripts/no-comments.mjs` чист.
- Обход шести страниц на четырёх ширинах со снимками в `web/.shots/`.
- Отдельный вывод одной фразой: чем эта витрина не похожа на страницу,
  сгенерированную по запросу «сделай лендинг для dev-инструмента». Если ответа
  нет — аудиты прошли зря.

### Что аудиты не лечат

Честно: аудит правит исполнение, а не замысел. Если страница читается как
шаблон из-за самой структуры — «шесть блоков подряд, у каждого заголовок слева и
панель справа», — никакой чек-лист этого не исправит. Такие вещи ловятся раньше,
на разборе замысла, и переделываются формой, а не полировкой. Поэтому по итогам
каждого аудита отдельно отвечаем на вопрос: это дефект исполнения или дефект
замысла — и второе чиним переделкой, а не правкой отступов.

## 13. Деплой проверен (6 сентября)

Заготовки инфраструктуры прогнаны по-настоящему: стек поднимался локально дважды
(minio + rules + rsocket + caddy), Caddyfile проверен `caddy validate`, workflows —
`actionlint`, remote-скрипты — прогоном в Linux.

### Что было сломано и починено

| Что | Чем грозило |
|---|---|
| Том `site` через `driver_opts: device:` | Контейнер падал при старте; `docker compose config` этого не показывал |
| Подмена каталога статики через `mv` | **Главная находка.** В Linux bind-монтирование держится за inode: выкладка отрабатывала бы «успешно», smoke-проверка проходила бы на старом сайте, а содержимое не менялось. Переведено на симлинк `current` |
| `header /index.html` | Заголовок не доставался никому: по `/index.html` никто не ходит, файл отдаёт `try_files`. Браузер кешировал разметку — ровно то, что заголовок должен был предотвратить |
| `request_body max_size 8MB` | Caddy считает `MB` десятичным: 8 000 000 против 8 388 608 у сервиса. Описание между этими размерами сервис принял бы, а Caddy отверг |
| Проверка запечённых прогонов через `git diff` | Не видела новых файлов: появись пятый провайдер — расхождение прошло бы молча. Переведено на `git status --porcelain` |
| Откат при неудачной выкладке | При отсутствии предыдущего выпуска «удавался», ничего не сделав. Теперь путь пишется до переключения, без него шаг падает явно |

### Что завести в GitHub перед первой выкладкой

Environment `production`; секреты `SSH_KEY`, `SSH_HOST`, `SSH_USER`; переменная
`SITE_URL`. Подробности — `web/infra/DEPLOY.md`.

### Открытый вопрос к команде (решение кейса не трогали)

Корневой `compose.yaml` публикует наружу порты `9000`, `9001`, `9292` — то есть
MinIO и сам сервис доступны в обход Caddy, включая запись правил, которую мы
закрыли. На VPS это стоит прикрыть файрволом (пускать только 80 и 443) либо
убрать `ports` у `minio` и `rsocket`: внутри сети Caddy достучится и без
публикации. **Правку их файла не делали — это их зона.**

### Не проверено локально

Настоящий SSH на VPS, выдача сертификата Let's Encrypt, `rsync` против живого
сервера, порты 80/443 (проверялось на 8080), запуск workflow в GitHub Actions.

### Ответ на главный вопрос приёмки

Чем витрина не похожа на сгенерированный лендинг: **здесь нечего пролистать —
каждый блок работающий прибор над настоящими данными, а не иллюстрация к
утверждению.** Лендинг сказал бы «умное сопоставление операций» и положил рядом
иконку; здесь поле ввода, куда вбиваешь `cancelPayout` и видишь, как veto
снимает кандидата, выигрывавшего по весам. И целый экран отдан тому, чего
инструмент **не понял**: заглушка, перечёркнутая роль, пять предупреждений на
nordbank. Сгенерированный лендинг не отдаёт экран под собственные провалы — он
продаёт; этот доказывает.

### Дефекты замысла — решение принято

1. **`/architecture` расформирована — сделано.** Конвейер переехал шапкой на
   `/lab` и связан со шагами: у стадии есть поле `steps`, клик подсвечивает и
   раскрывает нужный шаг разбора ниже. «Решения» ушли в `/docs` шестым пунктом
   меню. Маршрутов пять.
2. **`/rules` в две колонки — сделано.** Девять разделов сгруппированы в пять
   пунктов, состояние в адресе. Боковое меню вынесено в `shared/ui/SideNav.tsx`
   и переиспользовано на `/docs` — дублирования не осталось.
3. **`/rules` и `/docs` частично дублируют роль.** Граница «что такое правила»
   против «как их править» проходит внутри обеих страниц. После переделки
   раздела 1 и 2 пересмотреть: возможно, часть «как добавить правило» из `/docs`
   уместнее рядом с песочницей.

## 19. Замечания к решению кейса (не наша зона, для команды)

Найдено при сверке документации. **Ничего не правили** — это файлы команды.

   `rsocket` — внутри сети Caddy достучится и без публикации.

3. **`docs/context/` снесён целиком** тем же коммитом «начинаем заново». Вместе
   с ним пропали документы, которые писались под старое решение: журнал работы,

## 24. Визуальная концепция: Programa (6 сентября)

Замечание заказчика: сайт всё ещё читается как сгенерированный. Содержание
верное, механика честная, но визуально это «нейтральный технический интерфейс»
без характера — а такой и получается по умолчанию у любой генерации.

Взята готовая система с styles.refero.design — **Programa**, «Swiss design studio
at high noon». Полный референс сохранён в `web/design-ref/programa.md` (312 строк:
токены, компоненты, запреты, сетка).

### Почему именно она

Formulировка первоисточника: «белая галерейная стена, освещённая одной жёлтой
настольной лампой — всё серое, пока кнопка или подсветка не потребует внимания,
и тогда одна жёлтая нота держит всю комнату».

Это ровно наша логика, доведённая до предела: **цвет — сигнал, а не украшение.**
У нас уже так (киноварь = провайдер, ультрамарин = контракт, чернила = правило),
но система была мягкой. Programa даёт жёсткость: четыре серых плюс один
хроматический сигнал, никаких теней, hairline-границы, сетка 6px.

Плюс она снимает главную претензию: сайт выглядит **сделанным**, а не
собранным по шаблону, потому что у неё есть характер — швейцарская строгость,
доведённая до узнаваемости.

### Что берём

| Что | Как у нас будет |
|---|---|
| Ink Black `#1a1a1a` | текст, **все** границы, штрихи, разделители |
| Paper White `#ffffff` | полотно страницы, поверхности |
| Fog Gray `#f4f4f4` | единственная промежуточная поверхность |
| Ash Gray `#a3a3a3` | **только** placeholder и неактивное — не для текста |
| Сигнальный акцент | наш случай сложнее, см. ниже |
| Сетка 6px | все отступы кратны шести |
| Радиусы 10px / 16px | кнопки, поля, навигация / карточки |
| Ноль теней | высота передаётся границей и сменой поверхности |
| Трекинг −0.03em | на всех кеглях, включая крупные |

### Где отступаем от первоисточника, и почему

1. **Не один акцент, а два.** У Programa жёлтый — единственный сигнал. У нас
   цвет несёт смысл: киноварь = сторона провайдера, ультрамарин = сторона
   контракта. Отказаться от этого значит выбросить главное, что объясняет
   интерфейс. Поэтому: два семантических цвета вместо одного декоративного,
   но с их же дисциплиной — **только там, где обозначают сторону**, никогда
   для красоты.
2. **Гарнитура.** У них Neue Haas Grotesk. У нас Golos Text — кириллица родная,
   и это не обсуждается. Забираем не гарнитуру, а её применение: один шрифт на
   весь интерфейс, два начертания (400 и 500), тесный трекинг, иерархия весом,
   а не размером.
3. **Моноширинный остаётся.** У Programa одна гарнитура. У нас код, регулярки и
   значения полей — данные, которые обязаны читаться моноширинно. Это не
   «technical vibe», это функция.

### Что переделываем

- [x] **Токены** — палитра Programa, сетка 6px, радиусы 10/16, трекинг −0.03em.
- [x] **Ноль теней и блюра.** Сейчас `backdrop-filter` в липких панелях —
      заменить на сплошной фон и границу.
- [x] **Границы вместо мягкости.** Сейчас граница `--color-line` бледная;
      у Programa граница чернильная и определяет форму. Это самое заметное
      изменение: интерфейс станет чертёжным.
- [x] **Иерархия весом.** Проверить все заголовки: разница должна читаться
      весом 400/500 и размером по шкале, а не оттенками серого.

### Lighthouse после Programa (6 сентября)

| Страница | perf было → стало | a11y было → стало | CLS было → стало |
|---|---|---|---|
| `/` | 97 → 96 | **96 → 100** | 0.0003 |
| `/lab` | 86 → **89** | 100 | 0.0000 |
| `/rules` | 96 → 92 | 100 | 0.0000 |
| `/providers` | 98 → 86 | 100 | **0.0227 → 0.0008** |
| `/docs` | 93 → **94** | 100 | 0.0000 |

**Lighthouse соврал про причину.** CLS на `/providers` он приписывал загрузке
шрифта. Прогон с полностью заблокированными `gstatic` и `googleapis` дал ровно
те же цифры — атрибуция ложная. Настоящая причина: прогоны грузятся асинхронно,
в ячейках стоит плейсхолдер `…`, потом приходит `securitySchemes ApiKeyAuth
(api_key)` и строка вырастает на 109px. Лечится резервированием высоты строки.

**a11y 96 → 100 на главной.** Ловилось ровно то, что предполагалось: соперники
в сцене анимировались с `opacity: 0.2`, что даёт 1.35:1. Решено честно — они
теперь появляются **сдвигом**, а не проявлением из прозрачности; порог
непрозрачности 0.86. Не «спрятали от проверки», а убрали нечитаемое состояние.

**Убран последний `backdrop-filter`** в `.stage-controls` — недоделка перехода.

**Гипотезы, которые не подтвердились:** `layoutId`/`LayoutGroup` CLS не дают
вообще (это абсолютно спозиционированные декорации), CSS-счётчики по styleLayout
не бьют (461 мс при TBT 75).

**Почему `/lab` 89 и `/providers` 86 оставлены.** Остаток — LCP и TBT от парса
React с Motion под четырёхкратным троттлингом CPU. Дотянуть до 90 можно только
выкинув Motion, то есть убив всю анимацию, ради которой делался переход на
Programa. Цифра ради цифры того не стоит: CLS у обеих идеальный, a11y 100.

### Решение для команды: как убрать `tree` из справки

Проверено на копии в контейнере, код кейса не тронут. В `bin/rsocket` внутрь
класса `RsocketCLI` добавить одну строку:

```ruby
remove_command :tree
```

Важно: `hide_command` в Thor 1.5.0 **не работает** — такого метода класса
попросту нет, есть только `remove_command`. Обычный совет из интернета здесь
не подойдёт.
