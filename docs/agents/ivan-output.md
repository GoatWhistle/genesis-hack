# Иван — направление «выход»

Этот файл самодостаточный. Прочитай его целиком перед началом работы, дальше по ходу
сверяйся с ним же.

## Кто ты в проекте

Ты отвечаешь за то, что видит заказчик: сам сгенерированный код, инструкцию, примеры
данных, тесты. Судьи будут читать именно твой результат, и по нему судить обо всём
проекте. Некрасивый код стоит баллов.

Твои каталоги:

```
reference/                  образцовый сервис, написанный руками
lib/rsocket/runtime/        заглушки контракта заказчика
lib/rsocket/templates/      шаблоны
lib/rsocket/generate/       генераторы
spec/generate/              тесты на твой код
```

Чужое не трогай: `lib/rsocket/spec/`, `lib/rsocket/ir/`, `lib/rsocket/mock/`,
`examples/` — Амир. `lib/rsocket/classify/`, `dictionaries/`, `manifest/`, `report/` —
Савелий.

## Что делает проект целиком

Называется RSOCKET. Читает файл с описанием API платёжного сервиса и сам пишет готовый
код для подключения к нему. Сейчас разработчик делает это руками за 2–5 дней.

Обязательных файлов на выходе четыре, и три из них делаешь ты:

1. **Готовый класс на Ruby** — умеет отправить выплату, спросить статус, принять
   уведомление, проверить условия перед отправкой.
2. **Инструкция по подключению** — текстовый файл.
3. **Файл с примерами запросов и ответов.**
4. Команда для запуска — её делает капитан.

Сверх обязательного: файл с догадками инструмента, поддельный сервер, проверка кода
через него, сгенерированные тесты.

## Жёсткие правила, нарушение = снятие с хакатона

1. **Весь код только на Ruby.** Ни строчки на другом языке.
2. **Никаких нейросетей внутри решения.** Инструмент обязан давать один и тот же
   результат на одном и том же входе — иначе его нельзя проверить и держать в CI.
3. **Готовые библиотеки только опенсорсные и только гемы.**
4. **Никаких названий конкретных провайдеров в `lib/`.** Ни `novapay`, ни `payouts`, ни
   `sbp`. Каталог `templates/` — одно из двух исключений, там подстановки допустимы.
   В `generate/` названий быть не должно. На это есть тест, который падает при находке.

## Главное про порядок работы

Порядок обратный интуитивному, и это принципиально.

**Сначала пишем один сервис руками, доводим до состояния, которое не стыдно показать
Ruby-инженеру. Только потом превращаем его в шаблон.**

Не «пишем генератор и смотрим, что получится», а «получаем образец, который нам
нравится, и учим генератор его воспроизводить». Причина: в команде нет боевого опыта в
Ruby, и на глаз отличить хороший код от плохого мы не можем. Значит, вылизываем один
файл один раз — а дальше качество тиражируется автоматически.

Если начать с генератора, получится машинная каша, и мы даже не поймём, что это каша.

## Контракт заказчика

Из задания. Сгенерированный сервис обязан выглядеть так:

```ruby
class Provider
  class NovapayService < BaseService
    def check_conditions(operation, request_method)  # предпроверки
    def create_request(operation, request_method = 'create')  # создание выплаты
    def fetch_status(operation)  # запрос статуса
    def process_callback(payload)  # обработка уведомления
  end
end
```

Внутри, по примеру из задания: константа с адресом из переменной окружения, вызовы через
`client.post` и `client.get`, перехват ошибок провайдера, приватные сборщики тела
запроса, константы с картами статусов и ошибок, проверка подписи уведомления.

Статусы заказчика — всего три: `in_progress`, `approved`, `rejected`. Савелий отдаёт тебе
более полный набор (`created`, `processing`, `succeeded`, `rejected`, `cancelled`,
`refunded`, `needs_review`) — перевод в три делает твой шаблон.

## Что тебе приходит от остальных

От Амира — разобранное описание. От Савелия — догадки о ролях, статусах, ошибках,
единицах суммы. Контракт меняется только по согласию команды, с записью в
`docs/context/80-log.md`.

```ruby
Rsocket::Ir::Spec
  title, version, description
  servers          # [Server] — url, description, env (:sandbox | :production | :unknown)
  security_schemes # [SecurityScheme] — id, kind, location, name, description
  operations       # [Operation]
  raw_schemas      # { "CreatePayoutRequest" => Hash } — для сборки примеров по схеме
  notes            # [Note] — level (:info | :needs_confirmation | :unsupported), where, message

Rsocket::Ir::Operation
  http_method      # :get | :post | :put | :patch | :delete
  path             # "/payouts/{payout_id}"
  operation_id, tags, summary, description
  path_params, query_params, header_params  # [Field]
  request_fields   # [Field]
  request_examples # { "sbp_payout" => Hash }
  responses        # { 201 => Response, ... } — Response: code, description, fields, examples, headers
                   #   headers — заголовки ответа, например Retry-After у ошибки 429
  security         # ["ApiKeyAuth"]; пустой массив = метод открытый

Rsocket::Ir::Field
  name, type, format, description
  required         # true | false
  enum, pattern, minimum, maximum, max_length, example
  children         # [Field] — для объектов

                   #   verdict: :confident | :needs_confirmation | :unknown
```

Важно: роль может прийти с вердиктом «требует подтверждения» или «не определено». Твои
генераторы обязаны это пережить — не падать, а честно отразить в результате. Например,
если уведомлений у провайдера нет, инструкция должна прямо сказать, что их нет, а не
выдумывать раздел.

## Твои задачи

### T0.2 Заглушки контракта заказчика

Срок: сегодня, 3 сентября.

Сгенерированный сервис наследует `Provider::BaseService` — класс из системы заказчика,
которого у нас нет. Без заглушки сгенерированный код нельзя даже запустить, а значит
нельзя выполнить проверку через поддельный сервер.

`lib/rsocket/runtime/provider/base_service.rb` — воспроизводим контракт из задания:
четыре метода, помощники `success` и `failure`, поведение `check_conditions` по
умолчанию.

`lib/rsocket/runtime/provider/errors.rb` — `RateLimitError`, `UnauthorizedError`,
`ValidationError`, `InsufficientBalanceError`, `InternalError`.

`lib/rsocket/runtime/operation.rb` — дубль объекта операции заказчика: `id`, `amount`,
`currency`, `payout_requisite`, `provider_operation_id`.

`lib/rsocket/runtime/http_client.rb` — обёртка вокруг faraday, превращающая коды ответов
в эти ошибки.

Пиши с комментариями, откуда что взято: это наша реконструкция контракта заказчика по
примеру из задания, и жюри должно видеть, что мы понимаем, что делаем. На вопрос «откуда
вы знаете, что код подойдёт нашему контракту» ответ будет: мы генерируем против
документированной заглушки контракта из задания и прогоняем через неё проверку.

Готово, когда: файлы подключаются, объекты создаются, есть тест, что `failure` возвращает
ожидаемую форму.

### T0.3 Образцовый сервис, написанный руками

Срок: сегодня, 3 сентября. **Самая важная задача дня во всей команде.**

`reference/novapay_service.rb` — полностью рабочий сервис для NovaPay, написанный
руками так, как ты хочешь, чтобы выглядел результат генерации.

Что должно быть внутри:

- все четыре метода контракта
- адрес сервиса из переменной окружения со значением по умолчанию
- вход по ключу в заголовке `X-API-Key`
- ключ идемпотентности в заголовке `Idempotency-Key` при создании выплаты
- сборка тела запроса: сумма в копейках, валюта, идентификатор операции на нашей
  стороне, получатель со всеми полями
- обработка всех кодов ответа из описания API: 201, 400, 401, 402, 409, 422, 429, 500
- карта статусов провайдера в статусы заказчика
- карта ошибок: код ответа и код ошибки провайдера в наше действие
- проверка подписи уведомления, HMAC-SHA256 из заголовка `X-NovaPay-Signature`
- разбор уведомления: события `payout.completed`, `payout.failed`,
  `payout.processing`, `payout.cancelled`
- предпроверки: минимальная сумма 1000 рублей, то есть 100000 копеек

Требования к качеству:

- `bundle exec rubocop` на этом файле чистый
- в файле **не должно быть** ни одной подстановки вида `<%=` — это живой код, шаблон из
  него родится позже
- читается как нормальный Ruby, а не как заготовка

Готово, когда: линтер чистый; есть тесты на карту статусов и на разбор уведомления;
команда согласна, что показать не стыдно.

### T2.1 Шаблон сервиса из образца

Срок: 4 сентября после встречи с экспертами.

Берёшь `reference/novapay_service.rb` и превращаешь в
`lib/rsocket/templates/service.rb.erb`, подставляя всё, что берётся из разобранного
описания и догадок Савелия: адреса, имена методов, заголовки входа, карты статусов и
ошибок, поля тела запроса, схему подписи уведомления.

Готово, когда: шаблон, прогнанный на данных NovaPay, даёт файл, совпадающий с образцом по
смыслу.

### T2.2 Генератор сервиса

Срок: 4 сентября — утро 5 сентября.

`generate/service_generator.rb` плюс `generate/rubocop_pass.rb` — автоправка и проверка
линтером **внутри самого конвейера**. Не прошло проверку — громкая ошибка, а не тихое
предупреждение. Отчёт линтера идёт в выходные данные инструмента: это и контроль
качества, и аргумент на защите.

Готово, когда: для всех трёх описаний получается файл, проходящий `ruby -c` и линтер.

### T2.3 Генератор инструкции

Срок: 4 сентября — утро 5 сентября.

`templates/integration.md.erb` и `generate/docs_generator.rb`. Разделы строго как в
задании:

- как входить: тип, заголовок, где хранится ключ
- таблица методов: метод, адрес, назначение, идемпотентность
- перевод статусов: статус провайдера и статус заказчика
- обработка ошибок: код ответа, код провайдера, действие
- конфигурация шлюза
- схема подписи уведомлений

Плюс наш раздел: что инструмент не понял и что стоит проверить руками.

Готово, когда: инструкция для `swiftpay` честно говорит, что уведомлений у провайдера
нет, а не выдумывает раздел.

### T2.4 Генератор примеров данных

Срок: 4 сентября — утро 5 сентября.

`generate/fixtures_generator.rb`. Сценарии как в задании: создание запроса с ответами
201 и 422, запрос статуса, успешное уведомление, неуспешное уведомление, и для каждого
ожидаемый статус на нашей стороне.

Порядок выбора данных: сначала готовые примеры из описания, при их отсутствии — сборка
по описанию полей с соблюдением ограничений (`pattern`, `minimum`, перечисления).

Одинаковый вход обязан давать побайтово одинаковый выход — иначе инструмент нельзя
держать в CI и проверять сравнением.

Готово, когда: для всех трёх описаний получается файл со сценариями; повторный прогон
даёт тот же результат байт в байт.

### T3.4 Генератор тестов

Срок: 5 сентября, к встрече с экспертами в 13:00.

`templates/service_spec.rb.erb` и `generate/tests_generator.rb` — тесты поверх примеров

Готово, когда: сгенерированные тесты запускаются и зелёные для всех трёх описаний.

### T5.3 Показательный пример на два провайдера

Срок: 6 сентября.

Маленький скрипт, наглядно показывающий: один и тот же вызов прикладного кода работает
через два разных сгенерированных сервиса. Это самый сильный пункт защиты — он визуально
доказывает, что мы делаем единый разъём, а не клиента к одному API.

Готово, когда: скрипт запускается и на глазах отрабатывает через оба сервиса.

## Как работать

- Ветка на задачу, вливаем в `main` часто.
- Перед каждой встречей с экспертами (4, 5 и 6 сентября, окно 13:00–16:00) `main`
  обязан быть в рабочем состоянии.
- `bundle exec rubocop` чистый. Линтер и тесты заменяют нам ревью — не отключай правила
  ради зелёного.
- Каждый вечер запись в `docs/context/80-log.md`.
- Меняешь общую договорённость о виде данных — сначала скажи команде.
