# Амир — направление «вход»

Этот файл самодостаточный. Прочитай его целиком перед началом работы, дальше по ходу
сверяйся с ним же.

## Кто ты в проекте

Ты отвечаешь за то, чтобы файл с описанием API платёжного провайдера превратился в
удобную структуру данных, с которой дальше работают остальные. Всё, что связано с
чтением, разбором и раскладкой описания — твоё. Плюс поддельный сервер, потому что он
поднимается из того же разобранного описания.

Твои каталоги:

```
lib/rsocket/spec/      загрузка и раскладка
lib/rsocket/ir/        классы разобранного описания
lib/rsocket/mock/      поддельный сервер
examples/              примеры описаний API
spec/spec/             тесты на твой код
spec/mock/
```

Чужое не трогай: `lib/rsocket/classify/`, `dictionaries/`, `manifest/`, `report/` —
Савелий. `reference/`, `templates/`, `generate/`, `runtime/` — Иван. Если тебе нужно
что-то поменять у них, договариваемся, а не правишь молча.

## Что делает проект целиком

Называется RSOCKET. Читает файл с описанием API платёжного сервиса и сам пишет готовый
код для подключения к нему. Сейчас разработчик делает это руками за 2–5 дней.

На выходе инструмента четыре обязательных файла:

1. Готовый класс на Ruby, умеющий отправить выплату, спросить её статус и принять
   уведомление.
2. Инструкция по подключению в виде текста.
3. Файл с примерами запросов и ответов.
4. Команда для запуска, которая всё это делает за один проход.

Сверх обязательного мы делаем: файл с догадками инструмента, который человек может
поправить; поддельный сервер; проверку сгенерированного кода через этот сервер.

## Жёсткие правила, нарушение = снятие с хакатона

1. **Весь код только на Ruby.** Ни строчки на Python, Node или чём угодно ещё, даже во
   вспомогательных скриптах. Это прямой запрет организаторов.
2. **Никаких нейросетей внутри решения.** Ни облачных, ни локальных. Инструмент должен
   давать один и тот же результат на одном и том же входе. Писать код с помощью моделей
   можно, встраивать модель в продукт нельзя.
3. **Готовые библиотеки только опенсорсные и только гемы.** Утилиты не на Ruby под
   запретом.
4. **Никаких названий конкретных провайдеров в `lib/`.** Ни `novapay`, ни `payouts`, ни
   `sbp`. Исключения только два каталога: `dictionaries/` и `templates/`. На это есть
   тест, который падает при находке.

Правило 4 — самое важное для тебя. Судьи принесут своё описание API другого провайдера и
проверят инструмент живьём. Если где-то зашито NovaPay — сломается на глазах.

## Общая договорённость о виде данных

Это контракт между тремя направлениями. Ты его производишь, остальные потребляют.
Менять только по согласию всей команды, с записью в `docs/context/80-log.md`.

```ruby
Rsocket::Ir::Spec
  title, version, description
  servers          # [Server]
  security_schemes # [SecurityScheme]
  operations       # [Operation]
  raw_schemas      # { "CreatePayoutRequest" => Hash } — для сборки примеров по схеме
  notes            # [Note] — что не поняли уже на этапе чтения

Rsocket::Ir::Server
  url, description
  env              # :sandbox | :production | :unknown — по слову в описании и адресе

Rsocket::Ir::SecurityScheme
  id               # "ApiKeyAuth"
  kind             # :api_key | :bearer | :basic | :oauth2 | :unknown
  location         # :header | :query | :cookie | nil
  name             # "X-API-Key"
  description

Rsocket::Ir::Operation
  http_method      # :get | :post | :put | :patch | :delete
  path             # "/payouts/{payout_id}"
  operation_id     # "createPayout" или nil
  tags             # ["Payouts"]
  summary, description
  path_params      # [Field]
  query_params     # [Field]
  header_params    # [Field]
  request_fields   # [Field] — из тела запроса
  request_examples # { "sbp_payout" => Hash }
  responses        # { 201 => Response, 422 => Response, ... }
  security         # ["ApiKeyAuth"]; пустой массив = метод открытый

Rsocket::Ir::Response
  code, description
  fields           # [Field]
  examples         # { "completed" => Hash }
  headers          # [Field] — заголовки ответа, например Retry-After у ошибки 429

Rsocket::Ir::Field
  name, type, format, description
  required         # true | false
  enum, pattern, minimum, maximum, max_length, example
  children         # [Field] — для объектов
  item             # Field — для массивов
  path             # "recipient.phone" — полный путь через точку

Rsocket::Ir::Note
  level            # :info | :needs_confirmation | :unsupported
  where            # "paths./payouts.post.requestBody"
  message          # человекочитаемо, без трассировок стека
```

Важно про `security`: пустой массив и отсутствие поля — разные вещи. Пустой массив
означает, что метод намеренно объявлен открытым (так в описании помечен приём
уведомлений). Отсутствие означает наследование общей настройки. Различай.

## Твои задачи

### T0.4 Два своих описания API, специально непохожих

Срок: сегодня, 3 сентября. Никого не блокирует, можно делать первым.

Нужны два файла, которые ломают наши предположения. Без них универсальность инструмента
недоказуема, а судьи проверять будут именно её.

`examples/swiftpay/provider_api.yaml`:

- вход по токену в заголовке `Authorization: Bearer <token>`, а не по ключу в своём
  заголовке
- суммы дробным числом (`149.90`), а не в копейках целым
- уведомлений нет вообще — только опрос статуса
- статусы называются иначе: `new`, `sent`, `paid`, `declined`
- есть параметры в строке адреса у запроса статуса

`examples/kassabox/provider_api.yaml`:

- версия описания 3.1, а не 3.0
- операции названы непонятно: `makeTransfer`, `transferInfo`, `abortTransfer`
- ответ завёрнут в конверт: `{"data": {...}, "meta": {...}}`
- есть возврат средств, которого нет у остальных
- часть ошибок не описана вовсе
- два способа входа объявлены сразу

Требование: это честные, валидные описания, а не поддавки. Пиши их так, как если бы их
писал реальный провайдер со своими привычками.

Готово, когда: оба файла валидные, отличаются от NovaPay по всем перечисленным пунктам,
и ты сам понимаешь, какое место нашего инструмента каждый из них проверяет.

### T1.1 Чтение файла и разрешение ссылок

Срок: сегодня ночью, к утру 4 сентября.

`lib/rsocket/spec/loader.rb`. Читаем YAML через `Psych.safe_load` с включёнными
алиасами. Разрешение внутренних ссылок `$ref` пишем сами, гем не берём — решение
команды, обоснование в `docs/context/30-decisions.md`.

Что нужно уметь:

- обход локальных ссылок вида `#/components/schemas/Recipient`
- защита от кольцевых ссылок по глубине вложенности
- `allOf` — склеиваем в один набор полей
- `oneOf` и `anyOf` — берём первую ветку и пишем `Note` с уровнем
  `:needs_confirmation`, что была развилка
- внешние файловые ссылки — не поддерживаем, пишем `Note` с уровнем `:unsupported`,
  но **не падаем**
- версии описания 3.0 и 3.1 обе

Обработка ошибок — отдельный пункт критериев оценки, на нём дают баллы. Понятное
сообщение с указанием места, никогда не трассировка стека:

- битый YAML — сказать, в какой строке
- пустой файл
- нет раздела `paths`
- ссылка ведёт в никуда
- файла не существует, нет прав на чтение

Готово, когда: все три описания читаются; на каждый вид поломки есть тест; ни один не
даёт трассировку стека; кольцевая ссылка не вешает программу.

### T1.2 Раскладка в общий вид

Срок: к утру 4 сентября. Зависит от T1.1.

`lib/rsocket/spec/normalizer.rb` и все классы в `lib/rsocket/ir/` строго по
договорённости выше.

Тонкости:

- поля разбираются рекурсивно, у каждого проставляется полный путь через точку
  (`recipient.phone`)
- `required` берётся из списка `required` родительского объекта, а не из самого поля
- примеры вытаскиваются и из `examples` (множественного), и из `example`
  (единственного) — провайдеры пишут и так, и так
- `raw_schemas` сохраняем как есть: они нужны Ивану, чтобы собирать примеры данных по
  описанию полей, когда готовых примеров в файле нет
- `env` у сервера определяется по словам `sandbox`, `test`, `staging` в адресе и
  описании; не нашлось — `:unknown`, не выдумывай

Готово, когда: для NovaPay получается ровно 5 операций со всеми параметрами, ответами и
примерами; то же самое отрабатывает на двух твоих описаниях; всё покрыто тестами.

### T3.1 Поддельный сервер

Срок: 5 сентября, к встрече с экспертами в 13:00. Зависит от T1.2.

`lib/rsocket/mock/server.rb` на Rack (гем разрешён, решение команды записано).
`lib/rsocket/mock/responder.rb` — что отвечать.

Сервер поднимается из разобранного описания: маршруты берутся из путей, на каждый
описанный адрес отдаётся ответ. Порядок выбора ответа: сначала готовый пример из
описания, если его нет — собираем по описанию полей с соблюдением ограничений
(`pattern`, `minimum`, перечисления).

Подкоманда для ручного запуска: `bin/rsocket mock --spec ФАЙЛ --port 4010`.

Готово, когда: сервер поднимается по всем трём описаниям и отвечает на все описанные
адреса тем, что описание обещает.

### T3.2 Отправка уведомлений с подписью

Срок: 5 сентября.

Сервер умеет отправить уведомление на указанный адрес, подписав тело запроса тем же
способом, который проверяет сгенерированный код (для NovaPay это HMAC-SHA256, заголовок
`X-NovaPay-Signature`).

Это нужно, чтобы проверка подписи проверялась по-настоящему. Испорченная подпись обязана
отклоняться — сделай тест именно на это.

Готово, когда: правильная подпись принимается, испорченная отклоняется, и это покрыто
тестами.

### T4.1 и T4.4 Странные и поломанные описания

Срок: 5 сентября вечер — 6 сентября утро.

Тесты на поломанное: битый YAML, пустой файл, описание без методов, ссылка в никуда,
неизвестный способ входа, описание без единого примера. Каждое даёт понятное сообщение.

Ещё одно-два странных описания: без описанных ошибок, с параметрами в строке адреса
вместо тела запроса, с двумя способами входа сразу.

Готово, когда: инструмент не падает ни на одном из них, и по сообщению понятно, что не
так.

## Как работать

- Ветка на задачу, вливаем в `main` часто. Не копи большую ветку на два дня.
- Перед каждой встречей с экспертами (4, 5 и 6 сентября, окно 13:00–16:00) `main`
  обязан быть в рабочем состоянии.
- `bundle exec rubocop` должен быть чистым. У нас в команде нет боевого опыта в Ruby,
  поэтому линтер и тесты заменяют нам ревью — не отключай правила, чтобы стало зелёно.
- Каждый вечер короткая запись в `docs/context/80-log.md`: что сделал, что сломалось,
  что решил.
- Если меняешь общую договорённость о виде данных — сначала скажи команде.
