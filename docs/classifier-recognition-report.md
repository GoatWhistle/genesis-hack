# Проверка feat/classifier-recognition

## Текущий этап: исправления генератора после ec0f267

Работа начата с опубликованного `ec0f267`. Исправления классификатора из этого
коммита сохранены. Устаревшие выводы и результаты прежних этапов вынесены в
[classifier-recognition-history.md](classifier-recognition-history.md).

В этой рабочей директории `bench/` отсутствует. Результаты 71 описания из
предыдущего отчёта не выдаются за новый прогон. Эталоны, список провайдеров и
правила классификации ролей не менялись.

## Что исправлено и проверено

1. Параметр нового ресурса определяется относительно пути выбранного создания.
   `{code}`, `{payout}` и другие имена могут получать ID выплаты, если это
   дополнительный идентификатор того же ресурса. Родительский `account_id` и
   параметры выбора продукта не получают ID выплаты.
2. Все значения пути кодируются как отдельные сегменты. URL, `/`, `?`, `#` и
   пробелы внутри ID не изменяют маршрут. При отсутствующем параметре запрос
   не отправляется: Space Payments возвращает `provider.missing_parameter`,
   plain_client выбрасывает `ProviderError`.
3. Для параметров выбора продукта используются описанный default или единственное
   значение enum. Иначе Space Payments читает явно заданное значение из
   `operation.payout_requisite` по имени параметра, с предупреждением при сборке.
   Пример: `{"service" => "payments", "product" => "credit-transfer"}`.
   Непустой enum с несколькими вариантами автоматически не выбирается.
4. Имя идентификатора в маршруте статуса помогает найти соответствующее поле
   ответа создания, включая `batch_header.payout_batch_id`.
5. Если JSON-схема не описывает идентификатор, поддерживается объявленный заголовок
   `Location`: сохраняется последний сегмент пути созданного ресурса. Заголовки
   проходят через парсер, фикстуры и локальный StubServer. Успешный HTTP-ответ
   без пригодного ID больше не считается успешным созданием в обоих контрактах.
6. Путь к полю ответа сохраняет индексы массивов; ссылки в `items` раскрываются.
   Чтение массива допустимо только при одном элементе. Несколько платежей не
   приводят к произвольному выбору первого. Несовпадение формы ответа не вызывает
   String/Integer-исключение: неизвестный статус остаётся `in_progress`, отсутствие
   ID при создании приводит к отказу.
7. Статус и отмена читаются по собственной схеме ответа каждой роли.
8. Фикстуры нормализуют ключи `example` из схемы. Ожидаемый ID совпадает с реально
   отправленным JSON. Вложенные тела callback копируются независимо; генерация
   следующего сценария не изменяет предыдущий.
9. StubServer сопоставляет исходный закодированный путь: WEBrick-декодирование
   `%2F` больше не превращает URL-идентификатор в дополнительные сегменты.

Изменены оба шаблона — `space_payments` и `plain_client`. Источники параметров
задаются контрактом; неизвестные параметры plain_client остаются явным TODO и
дают ошибку до сети. Этот интерфейс не получил неявного аргумента реквизитов.

export LANG=en_US.UTF-8
export BUNDLE_PATH=vendor/bundle
export BUNDLE_WITHOUT=classifiers

## Ограничения и рекомендация

- GOV.UK Pay исправлен на этапе `ec0f267`; старый текст «не исправлен» относится
  только к первоначальному `cc8473b` и сохранён в архиве.
- На корпусе `ec0f267` оставались неправильные операции, пропуски статуса/отмены,
  спорные эталоны и многошаговые сценарии. В этом этапе они не переоценивались.
- Неизвестные обязательные поля payload остаются TODO. Рабочий маршрут и
  успешная проба на собственных фикстурах не доказывают исполнение выплаты.
- Выбор из нескольких элементов массива и распознавание недокументированного ID
  требуют дополнительных доказательств. Автоматический выбор не добавлялся.
- Нужен повтор `bundle exec ruby bench/measure.rb bench/truth.yml bench/truth-new.yml`
  и сквозной прогон 71 описания в рабочей директории с корпусом. Использовавшаяся
  при настройке группа holdout не является независимой проверкой.

Текущие исправления генератора готовы к review по локальным проверкам. Общую
ветку нельзя объявлять production-готовой; решение о слиянии требует повторного
корпуса и оценки нужных бизнес-сценариев. `main`/`deploy` и платёжные API не затрагивались.
