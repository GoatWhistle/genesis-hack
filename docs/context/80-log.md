# Журнал хода хакатона

Рабочий журнал основного этапа, 3–6 сентября. Пишется по ходу дела: что выяснили, что
сделали, что сломалось, что решили. Отличие от [30-decisions.md](30-decisions.md) —
туда попадают только принятые решения с обоснованием, сюда всё остальное, включая
тупики и наблюдения.

Формат записи: дата и время, короткий заголовок, суть. Новые записи добавляются вниз.

## 2 сентября, канун

Прочитан чат хакатона целиком. Факты перенесены в

Главное на завтра: полное описание задачи открывается в 15:00, QA-сессия в 19:30.
Вопросы к сессии подготовлены в [40-open-questions.md](40-open-questions.md).

## 3 сентября

Полное описание задачи получено: `провайдер_api.yaml` плюс `описание.docx`. Разобрано,
сведено с нашей концепцией в [90-build-plan.md](90-build-plan.md) — структура
репозитория, правила по стадиям, порядок работ по дням с привязкой к чек-поинтам.

Главное из брифа, чего мы не знали до 15:00: обязательных артефактов ровно четыре
(сервис, `INTEGRATION.md`, `fixtures.json`, CLI), контракт `Provider::BaseService`
приведён в брифе с примером реализации, критерии оценки расписаны по пунктам с баллами.
Наш `mapping.yml`, мок-сервер и шаг верификации в обязательный минимум не входят —
остаются дифференциаторами и заходят в пункты про универсальность, сообщение о
неоднозначном и отраслевые «дополнительные идеи».

Закрыты три открытых вопроса по реализации, записаны в
[30-decisions.md](30-decisions.md): разбор спецификации пишем сами без гема, проект
оформляем гемом, мок-сервер только на Ruby.

Отдельно про мок-сервер: обсуждался вариант написать его на Python ради скорости.
Отклонён как прямое нарушение правил — сообщение 263 запрещает любой не-Ruby код в
сдаваемом решении. Вопрос про Prism на QA-сессии всё равно задаём, но теперь скорее для
протокола: свой на Ruby пишем в любом случае.
