# Задачи команды

Составлено 3 сентября 2026 на основе [90-build-plan.md](90-build-plan.md). Задачи
разбиты так, чтобы люди работали параллельно и почти не ждали друг друга.

## Как делим работу

Три направления, распределены 3 сентября. Каждый ведёт своё от начала до конца.

| Направление | Кто | Что делает | Задание |
|---|---|---|---|
| **Вход** | Амир | Читает файл с описанием API, разрешает ссылки, раскладывает в общий вид. Плюс два своих описания для проверки универсальности и поддельный сервер | [amir-input.md](../agents/amir-input.md) |
| **Мозг** | Савелий | Определяет по описанию, что за что отвечает: признаки, оценка, вердикты, статусы, ошибки, единицы суммы, файл с догадками, отчёт | [savely-brain.md](../agents/savely-brain.md) |
| **Выход** | Иван | Образцовый сервис руками, заглушки контракта заказчика, шаблоны, генераторы сервиса, инструкции, примеров данных и тестов | [ivan-output.md](../agents/ivan-output.md) |
| **Сборка** | Капитан | Каркас проекта, командная строка, проверяльщик, README, сценарий показа | — |

Файлы в `docs/agents/` написаны так, чтобы агент каждого участника стартовал с нуля,
прочитав только свой файл: там повторены и правила хакатона, и общая договорённость о
виде данных, и задачи с критериями готовности.

Правила совместной работы:

- Ветка на задачу, вливаем в `main` часто, не копим неделю.
- Перед чек-поинтом `main` обязан быть в показуемом состоянии. Приведение к нему —
  отдельная запланированная работа, а не «само получится».
- Каждый вечер запись в [80-log.md](80-log.md): что сделали, что сломалось, что решили.
- На каждом чек-поинте задаём экспертам один заготовленный вопрос про приоритеты
  оценки и записываем ответ дословно.

## Общая договорённость: как выглядит разобранное описание

Это самое важное в документе. Пока эта договорённость не зафиксирована, параллельная
работа невозможна: «вход» отдаёт именно это, «мозги» и «выход» именно это принимают.
Меняется только по общему согласию, с записью в [80-log.md](80-log.md).

```ruby
Rsocket::Ir::Spec
  title, version, description
  servers          # [Server]
  security_schemes # [SecurityScheme]
  operations       # [Operation]
  raw_schemas      # { "CreatePayoutRequest" => Hash } — для сборки примеров по схеме
  notes            # [Note] — что не поняли уже на этапе чтения

Rsocket::Ir::Server
  url, description
  env              # :sandbox | :production | :unknown — по слову в описании и адресе

Rsocket::Ir::SecurityScheme
  id               # "ApiKeyAuth"
  kind             # :api_key | :bearer | :basic | :oauth2 | :unknown
  location         # :header | :query | :cookie | nil
  name             # "X-API-Key"
  description

Rsocket::Ir::Operation
  http_method      # :get | :post | :put | :patch | :delete
  path             # "/payouts/{payout_id}"
  operation_id     # "createPayout" или nil
  tags             # ["Payouts"]
  summary, description
  path_params      # [Field]
  query_params     # [Field]
  header_params    # [Field]
  request_fields   # [Field] — из тела запроса
  request_examples # { "sbp_payout" => Hash }
  responses        # { 201 => Response, 422 => Response, ... }
  security         # ["ApiKeyAuth"]; пустой массив = метод открытый

Rsocket::Ir::Response
  code, description
  fields           # [Field]
  examples         # { "completed" => Hash }
  headers          # [Field] — заголовки ответа, например Retry-After у ошибки 429

Rsocket::Ir::Field
  name, type, format, description
  required         # true | false
  enum, pattern, minimum, maximum, max_length, example
  children         # [Field] — для объектов
  item             # Field — для массивов
  path             # "recipient.phone" — полный путь через точку

Rsocket::Ir::Note
  level            # :info | :needs_confirmation | :unsupported
  where            # "paths./payouts.post.requestBody"
  message          # человекочитаемо, без трассировок стека
```

Что отдают «мозги»:

```ruby
Rsocket::Classify::Result
  roles            # { :create_payout => RoleAssignment, ... }
  statuses         # [StatusMapping]
  errors           # [ErrorMapping]
  money            # MoneyDecision
  webhook          # WebhookInfo | nil
  notes            # [Note]

RoleAssignment
  role             # :create_payout | :fetch_status | :cancel | :refund | :balance | :webhook
  operation        # Ir::Operation
  score            # Float
  verdict          # :confident | :needs_confirmation | :unknown
  evidence         # [Evidence]

Evidence
  signal           # :lexicon | :signature | :lifecycle
  detail           # "имя операции содержит payout"
  weight           # Float

StatusMapping
  provider_value   # "completed"
  canonical        # :succeeded
  verdict, evidence

ErrorMapping
  http_code        # 429
  provider_code    # "rate_limit_exceeded" | nil
  klass            # :retryable | :final | :auth | :validation | :limit
  evidence

MoneyDecision
  unit             # :minor | :decimal
  field_path       # "amount"
  evidence

WebhookInfo
  operation
  signature_header # "X-NovaPay-Signature"
  algorithm        # :hmac_sha256 | :unknown
  event_field      # "event"
  status_field     # "status"
```

Наш набор канонических статусов шире, чем у заказчика: `created`, `processing`,
`succeeded`, `rejected`, `cancelled`, `refunded`, `needs_review`. В брифе у заказчика
всего три — `in_progress`, `approved`, `rejected`. Перевод из нашего набора в их три
делает шаблон сервиса, а не классификатор. Так мы не теряем смысл и при этом выдаём то,
что требует бриф.

## Стадия 0. Сегодня, 3 сентября

Цель: есть каркас, есть образцовый код, есть на чём проверять универсальность.

### T0.1 Каркас проекта

Направление: любой, делается первым и быстро, остальные его ждут.

`Gemfile`, `rsocket.gemspec`, `Rakefile`, `.rubocop.yml`, все каталоги из
[90-build-plan.md](90-build-plan.md), `bin/integrate` и `bin/rsocket` заглушками,
`lib/rsocket/version.rb`, `lib/rsocket/errors.rb`.

Гемы в `Gemfile`: `thor`, `faraday`, `rack`, `rackup`, `rspec`, `webmock`, `rubocop`.

Готово, когда: `bundle install` проходит, `bundle exec rspec` запускается (пусть ноль
тестов), `bundle exec rubocop` без замечаний, `bundle exec bin/integrate --help`
печатает справку.

### T0.2 Заглушки контракта заказчика

Направление: выход.

`lib/rsocket/runtime/provider/base_service.rb` — воспроизводим контракт из брифа: четыре
метода, помощники `success` и `failure`, поведение `check_conditions` по умолчанию.
`runtime/provider/errors.rb` — `RateLimitError`, `UnauthorizedError`,
`ValidationError`, `InsufficientBalanceError`, `InternalError`.
`runtime/operation.rb` — дубль объекта операции: `id`, `amount`, `currency`,
`payout_requisite`, `provider_operation_id`. `runtime/http_client.rb` — обёртка вокруг
faraday, превращающая коды ответов в эти ошибки.

Всё с комментариями, откуда взято: это наша реконструкция контракта заказчика по
примеру из брифа, и жюри должно видеть, что мы это понимаем.

Готово, когда: файлы подключаются, объекты создаются, есть тест на то, что `failure`
возвращает ожидаемую форму.

### T0.3 Образцовый сервис, написанный руками

Направление: выход. Самая важная задача дня.

`reference/novapay_service.rb` — полностью рабочий сервис для NovaPay, написанный
руками так, как мы хотим, чтобы выглядел результат генерации. Все четыре метода,
подпись вебхука, карты статусов и ошибок, приватные сборщики тела запроса, обработка
всех кодов ответа из описания API.

Требование: `bundle exec rubocop` на этом файле чистый, и файл читается как нормальный
Ruby, а не как заготовка под шаблон. Никаких `<%=` в нём быть не должно — это код, из
которого шаблон родится позже.

Готово, когда: код проходит линтер, покрыт тестом на карты статусов и на разбор
уведомления, и мы согласны, что не стыдно показать.

### T0.4 Ещё два описания API, специально непохожих

Направление: вход. Не блокирует никого, можно делать параллельно.

`examples/swiftpay/provider_api.yaml` — другой способ входа (токен в заголовке
`Authorization: Bearer`), суммы дробным числом а не в копейках, вебхука нет вообще,
статусы называются иначе (`new`, `sent`, `paid`, `declined`).

`examples/kassabox/provider_api.yaml` — версия описания 3.1, операции названы
непонятно (`makeTransfer`, `transferInfo`, `abortTransfer`), ответ завёрнут в конверт
(`{"data": {...}, "meta": {...}}`), есть возврат средств, часть ошибок не описана.

Требование: это честные описания, а не поддавки. Их задача — сломать наш инструмент до
того, как его сломает жюри.

Готово, когда: оба файла читаются как валидные описания API и заметно отличаются от
NovaPay по всем перечисленным пунктам.

### T0.5 Словари

Направление: мозги.

`dictionaries/operations.yml` — роль и её синонимы в именах, путях, тегах.
`dictionaries/statuses.yml` — значения статусов провайдеров и наш канонический.
`dictionaries/errors.yml` — ключевые слова кодов ошибок и класс ошибки.
`dictionaries/money.yml` — слова-признаки копеек и центов.
`dictionaries/weights.yml` — вес каждого признака и два порога.

Наполнять не из головы, а глядя на реальные описания платёжных API. Чем больше
посмотрели, тем полнее словарь.

Готово, когда: файлы читаются кодом, покрывают все три наших примера, и добавление новой
роли не требует правок в коде.

## Стадия 1. Ночь и утро 4 сентября — к чек-поинту 1

Цель: `bundle exec bin/rsocket analyze --spec examples/novapay/provider_api.yaml`
печатает отчёт и пишет `mapping.yml`. То же самое не падает на двух других описаниях.

### T1.1 Чтение файла и разрешение ссылок

Направление: вход. Зависит от T0.1.

`spec/loader.rb`: чтение YAML, свой обход `$ref` по локальным ссылкам, защита от
кольцевых ссылок по глубине, склейка `allOf`, первая ветка из `oneOf` и `anyOf` с
записью неоднозначности. Внешние файловые ссылки — запись «не поддерживаем», не падение.

Понятные сообщения об ошибках: битый YAML с указанием строки, отсутствие
`components/schemas`, ссылка в никуда.

Готово, когда: все три описания читаются, есть тесты на каждый вид поломки, ни один не
даёт трассировку стека.

### T1.2 Раскладка в общий вид

Направление: вход. Зависит от T1.1.

`spec/normalizer.rb` и все классы в `ir/` строго по договорённости выше. Поля разбираются
рекурсивно с полным путём через точку. Примеры вытаскиваются и из `examples`, и из
`example`.

Готово, когда: для NovaPay получается 5 операций со всеми параметрами, ответами и
примерами, и это покрыто тестами.

### T1.3 Признак «по словам»

Направление: мозги. Зависит от T0.5 и договорённости о виде данных, но не от готовности
T1.2 — работать можно на заглушке.

`classify/signals/lexicon.rb`: сверка имени операции, пути, тегов и описания со
словарём. Каждое совпадение — отдельный признак с человекочитаемой формулировкой.

Готово, когда: на NovaPay находит создание, статус, отмену и баланс; на kassabox с его
непонятными именами находит меньше — и это правильно.

### T1.4 Признак «по форме запроса и ответа»

Направление: мозги.

`classify/signals/signature.rb`: правила из [90-build-plan.md](90-build-plan.md). Это
главный признак — он работает там, где имена бесполезны.

Готово, когда: на kassabox определяет роли правильно, несмотря на непонятные имена
операций.

### T1.5 Признак «по связям через номера»

Направление: мозги.

`classify/signals/lifecycle.rb`: строим связи — какая операция выдаёт номер, какие
операции этот номер принимают в пути. Отсюда вывод, кто создаёт ресурс, а кто его читает.

Готово, когда: на всех трёх описаниях правильно указывает создающую операцию, ни разу не
опираясь на слова.

### T1.6 Оценка, пороги, вердикт

Направление: мозги.

`classify/evidence.rb`, `scoring.rb`, `roles.rb`, `classifier.rb`. Сумма весов, два
порога из `weights.yml`, три вердикта. Ниже нижнего порога — «не определено», не
догадка. Конфликты, когда две операции метят в одну роль, разрешаются по оценке, и
проигравшая попадает в отчёт.

Готово, когда: на всех трёх описаниях вердикты разумные, и ни одна роль не назначена
уверенно по одному слабому признаку.

### T1.7 Статусы, ошибки, единицы суммы

Направление: мозги.

`status_mapper.rb`, `error_mapper.rb`, `money_detector.rb` по правилам из плана. Для
суммы — совокупность признаков: целое число, слова в описании, порядок величины
минимума и примера.

Готово, когда: на NovaPay определяются копейки, на swiftpay — дробное число, и оба
вывода попадают в отчёт с обоснованием.

### T1.8 Файл с догадками

Направление: мозги. Зависит от T1.6.

`manifest/writer.rb` пишет `mapping.yml`: роли, статусы, ошибки, единицы суммы,
вебхук — каждое с вердиктом и признаками словами. `manifest/reader.rb` читает обратно,
и правка человека всегда важнее автоматического вывода.

Готово, когда: файл понятен человеку, который не читал наш код, а правка роли в файле
меняет результат следующего прогона.

### T1.9 Отчёт

Направление: любой.

`report/report.rb` собирает находки со всех стадий в три ведра: понято уверенно,
требует подтверждения, не поддержано. `report/terminal.rb` печатает это человеку.

Готово, когда: на kassabox отчёт честно перечисляет всё непонятое, и по нему видно, что
делать дальше.

### T1.10 Команда `analyze`

Направление: любой. Зависит от T1.2, T1.6, T1.8, T1.9.

`cli.rb` на thor, подкоманда `analyze --spec ПУТЬ [--out КАТАЛОГ]`: читает, разбирает,
классифицирует, пишет `mapping.yml`, печатает отчёт.

Готово, когда: работает на всех трёх описаниях. **Это то, что показываем на чек-поинте 1.**

### T1.11 Тест против зашитых названий

Направление: любой.

`spec/no_hardcode_spec.rb`: ищет в `lib/` слова конкретных провайдеров и их полей
(`novapay`, `payouts`, `sbp`, `swiftpay`, `kassabox`) и падает при находке. Исключения —
только `dictionaries/` и `templates/`.

Готово, когда: тест зелёный, а если специально зашить название — краснеет.

## Стадия 3. 5 сентября до чек-поинта 2

Цель: сгенерированный код проверен на поддельном сервере, тесты зелёные.

### T3.1 Поддельный сервер

Направление: любой. Зависит от T1.2.

`mock/server.rb` на Rack: маршруты из описания, `mock/responder.rb` отвечает примером из
описания, при отсутствии — собранным по описанию полей. Подкоманда
`bin/rsocket mock --spec ФАЙЛ --port 4010`.

Готово, когда: сервер поднимается по всем трём описаниям и отвечает на все описанные
адреса.

### T3.2 Отправка уведомлений с подписью

Направление: любой.

Сервер умеет отправить уведомление на наш адрес, подписав тело тем же способом, который
проверяет сгенерированный код. Проверка подписи должна проверяться по-настоящему, а не
формально.

Готово, когда: правильная подпись принимается, испорченная отклоняется.

### T3.3 Проверяльщик

Направление: любой. Зависит от T3.1, T2.2.

`verify/verifier.rb`: поднимает поддельный сервер, прогоняет сценарий целиком —
создание выплаты, запрос статуса, приход уведомления, перевод в статус заказчика — и
сверяет с ожидаемым. Подкоманда `bin/rsocket verify`.

Готово, когда: зелено на всех трёх описаниях, и поломка образца ломает проверку.

### T3.4 Генератор тестов

Направление: выход.
