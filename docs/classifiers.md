# Способы распределения ролей: результаты замера

Роли контракта распределяются одним из трёх способов: правилами с весами, косинусовой
близостью эмбеддингов или запросом в Claude. Интерфейс у них общий: классификатор
возвращает привязки ролей, дальнейший конвейер одинаков. Различаются точность, скорость и
стоимость; файл содержит результаты измерения.

Замер прогнан 6 сентября 2026 года. Воспроизводится одной командой:

```
make bench                             # все три способа, все описания
make bench KINDS="rules embeddings"    # только эти
BENCH_RUNS=5 make bench                # прогонов на способ
BENCH_PROVIDERS=quantumpay make bench  # только одно описание
```

Сетевым способам нужны ключи: `VOYAGE_API_KEY` для эмбеддингов, `ANTHROPIC_API_KEY`
(и `ANTHROPIC_BASE_URL`, если ходим через прокси) для модели. Сам harness —
[bench/classifiers.rb](../bench/classifiers.rb).

Оба сетевых способа и harness замера находятся вне репозитория: сборка не должна зависеть
от сети и внешних ключей. Файл содержит результаты их измерения и обоснование выбора
правил как способа по умолчанию.

Ниже разобран один прогон. Исходные данные — [bench/results/](../bench/results/): вывод
harness, окружение, разбивка по проходам и стоимость прогона.

## Состав выборки

| Описание     | Откуда                       | Операций | Чем интересно                                          |
| ------------ | ---------------------------- | -------- | ------------------------------------------------------ |
| `novapay`    | `examples/`                  | 5        | единственное с описанным webhook                       |
| `swiftpay`   | `examples/`                  | 3        | webhook не описан, правильный ответ — пустая роль      |
| `kassabox`   | `examples/`                  | 4        | есть возврат средств, похожий на создание выплаты      |
| `nordbank`   | `examples/`                  | 4        | есть баланс, не занимающий ролей                       |
| `quantumpay` | `bench/unseen/`              | 5        | **не участвовало в составлении правил**                |

Первые четыре описания использовались при составлении `base.yml`. Результат 16 из 16 на
них предопределён составом словаря и не характеризует качество правил.

Пятое описание добавлено для проверки поведения на неизвестной лексике. Те же четыре
операции названы словами, отсутствующими в словаре: `enqueue` вместо `create`, `halt`
вместо `cancel`, `revoke` и `abort`, `signal` вместо `webhook` и `callback`. Русских
описаний в нём нет. Описание синтетическое и проверяет один сценарий: поведение при
непредусмотренном написании.

## Точность

Верная разметка — та же, что проверяют юнит-тесты: 4 роли на описание, 20 всего.

| способ       | novapay | swiftpay | kassabox | nordbank | quantumpay | всего     |
| ------------ | ------- | -------- | -------- | -------- | ---------- | --------- |
| `rules`      | 4/4     | 4/4      | 4/4      | 4/4      | **1/4**    | 17/20     |
| `embeddings` | 4/4     | 4/4      | 4/4      | 4/4      | **3/4**    | 19/20     |
| `llm`        | 4/4     | 4/4      | 4/4      | 4/4      | **4/4**    | **20/20** |

На описаниях из `examples/` результаты совпадают: 16 из 16 у каждого способа, включая три
случая, где верный ответ — оставить роль незанятой. Различия проявляются только на пятом
описании.

**Правила на незнакомом описании теряют три роли из четырёх.** Причём `create_request` —
роль обязательная, так что сборка не просто ошибается, а останавливается:

```
create_request    — лучший кандидат enqueue_disbursement набрал 4 при пороге 10
fetch_status      disbursement_snapshot  счёт 8: http_method =~ /\Aget\z/, path =~ /\{[^}]+\}\z/
process_callback  — лучший кандидат enqueue_disbursement набрал 1 при пороге 8
cancel_request    — лучший кандидат enqueue_disbursement набрал 1 при пороге 8
```

Единственная назначенная роль определена по форме операции, а не по лексике: `GET` и
параметр в конце пути дают ровно 8 очков при пороге 8. Это ожидаемое поведение: правила
распознают только то, что перечислено в словаре, а `enqueue` в нём отсутствует.
Исправляется добавлением слова в `base.yml` после ручного разбора описания.

**Эмбеддинги теряют одну роль и промахиваются на 0.005.** Близость
`fetch_status × disbursement_snapshot` — 0.645 при пороге 0.65:

|                         | create | fetch     | callback | cancel |
| ----------------------- | ------ | --------- | -------- | ------ |
| `enqueue_disbursement`  | 0.799  | 0.603     | 0.609    | 0.685  |
| `disbursement_snapshot` | 0.737  | **0.645** | 0.587    | 0.661  |
| `halt_disbursement`     | 0.763  | 0.616     | 0.620    | 0.804  |
| `disbursement_signal`   | 0.772  | 0.652     | 0.721    | 0.699  |
| `ledger_snapshot`       | 0.721  | 0.590     | 0.534    | 0.631  |

Порог 0.64 дал бы 20 из 20, но такое изменение — подгонка под описание, на котором
проверялось обобщение. Существеннее ширина окна: на пяти описаниях допустимый порог лежит
в `(0.628, 0.645]`, то есть в интервале 0.017. Шкала Voyage сжата в диапазон 0.53–0.87,
несовпадающие пары дают около 0.6, запас у порога отсутствует. Шестое описание с большой
вероятностью сделает интервал пустым. Порог вынесен в `RSOCKET_EMBEDDING_THRESHOLD` и
требует подбора под корпус.

**Модель разметила все описания верно, включая незнакомое,** и сформулировала обоснование
каждой роли: «остановка перевода до передачи в банк — это отмена». Обоснование
записывается в `mapping.yml` в поле `why` и пригодно для ручной проверки без обращения к
списку сработавших регулярок.

## Скорость

Медиана времени самой разметки одного описания.

| способ       | на `examples/` | на незнакомом | минимум за все прогоны |
| ------------ | -------------- | ------------- | ---------------------- |
| `rules`      | **22 мкс**     | 59 мкс        | 19 мкс                 |
| `embeddings` | 1.85 с         | 2.69 с        | **602 мс**             |
| `llm`        | 15.62 с        | 27.07 с       | **10.43 с**            |

Остальной конвейер — чтение описания, раскрытие `$ref`, все решения о сборке и печать
четырёх файлов — занимает 4–6 мс. Отсюда доля разметки в сборке:

| способ       | сборка целиком | из неё разметка |
| ------------ | -------------- | --------------- |
| `rules`      | ~5 мс          | 0.4 %           |
| `embeddings` | ~0.6 с         | 99 %            |
| `llm`        | ~15.6 с        | 99.97 %         |

Правила быстрее эмбеддингов примерно в 27 000 раз и быстрее модели в 700 000 раз.
Значим порядок величины: время разметки правилами пренебрежимо мало относительно сборки,
время любого сетевого способа определяет время сборки целиком.

Разброс у эмбеддингов (602 мс против медианы 1.85 с) вызван ограничением бесплатного
тарифа Voyage — три запроса в минуту. Harness выдерживает паузу 21 секунду, лимит
срабатывает и при ней, часть замеров включает ожидание. Задержка одного запроса без
ожидания — 0.6–0.8 с.

Разброс у модели — 10.4–29.7 с; наибольшее время приходится на незнакомое описание.

## Цена

| способ       | токенов на описание               | одно описание | 1000 описаний |
| ------------ | --------------------------------- | ------------- | ------------- |
| `rules`      | —                                 | $0            | **$0**        |
| `embeddings` | 445                               | $0.00001      | **$0.01**     |
| `llm`        | 4 000 на вход, 1 630 на выход     | $0.054        | **$54**       |

Эмбеддинги дешевле модели примерно в 5 000 раз. Структура расхода модели:

- **76 % стоимости приходится на выход.** На четыре строки JSON расходуется около
  1 630 токенов, включая рассуждения. Управляется через `RSOCKET_LLM_EFFORT`; замер
  выполнен на значении `low` — минимальном, поэтому дальнейшее снижение возможно только
  сменой модели.
- **Около 80 % входа не относится к запросу инструмента.** Запрос со списком ролей и
  операций занимает 820–880 токенов, на вход уходит около 4 000; разница добавляется
  прокси. При прямом обращении к api.anthropic.com вход должен быть примерно вчетверо
  меньше, стоимость — примерно вдвое.

## Выводы

**Правила остаются способом по умолчанию.** На описаниях, близких к тем, по которым они
составлялись, результат совпадает с результатом модели при нулевой стоимости,
пренебрежимо малом времени и воспроизводимости результата между прогонами.

**Преимущество сетевых способов проявляется на незнакомой лексике**, а не в точности на
знакомой. Правила в этом случае останавливают сборку на обязательной роли: остановка
предпочтительнее произвольного назначения, но требует ручного разбора описания и правки
`base.yml`.

Отсюда возможная схема применения: **правила первым проходом, модель — вторым, когда
правила не заняли обязательные роли.** Стоимость и задержка возникают только на
описаниях, которые иначе привели бы к остановке. На данной выборке это одно описание из
пяти.

Эмбеддинги в такой схеме занимают промежуточное положение: дешевле модели в 5 000 раз, но
обобщают хуже и требуют порога без запаса. Применимы там, где задержка в 15 секунд
неприемлема.

## Оговорки

- **Выборка из пяти описаний недостаточна.** Четыре из них использовались при
  составлении правил. Результат «17 из 20» характеризует эту выборку, а не поведение на
  произвольном провайдере.
- **`quantumpay` составлен искусственно** так, чтобы правила на нём ошибались. Он
  показывает поведение в таком случае, но не частоту его возникновения. Оценка частоты
  требует чужих описаний: подобранные кандидаты и результаты по ним — в
  [bench/candidates.md](../bench/candidates.md). По этим данным из пяти настоящих
  описаний правила не собрали бы четыре, причём причина — не отдельное незнакомое слово,
  а способ именования операций.
- **Три прогона на способ.** Достаточно для медианы задержки, недостаточно для хвостов
  распределения.
- **Модель недетерминирована.** Один запрос может дать разную разметку; 20 из 20 —
  результат конкретного прогона.
- **Обращение шло через прокси**, а не напрямую в Anthropic. Это увеличивает задержку и
  стоимость; на точность влиять не должно.

# Второй замер: 41 описание, из них 36 внешних

Первый замер выполнен на пяти описаниях, четыре из которых использовались при
составлении правил, а вывод о поведении на незнакомой лексике опирался на один
синтетический пример. Во втором замере добавлены 36 описаний реальных провайдеров из
`bench/specs/`: Adyen, PayPal, Stripe, Square, ЮKassa, Paystack, Velo, Fire, Open Banking
UK и Швейцарии, Interledger и около пятнадцати описаний без выплат.

Эталонная разметка — `bench/truth.yml`, составлена вручную по спискам операций. Описания
разделены на три группы: **20 с выплатами** (проверяются все четыре роли), **21 без
выплат** (верный результат — не назначить ролей и остановить сборку) и **4 исключённых**:
два каталога банка, где выплате соответствуют три разные операции, и два, которые не
читает загрузчик.

## Изменения в правилах

Первый прогон на внешних описаниях дал **6 верных сборок из 20, 11 неверных и 14 верных
отказов из 21**. Разбор выявил две системные причины; обе устранены изменением состава
проверяемых признаков, а не расширением словаря.

**Первое: имя операции не сводится к `operationId`.** Правило `\A(create|make|submit|…)`
требовало глагол в начале `operationId`. Провайдеры называют операции от ресурса, а не от
действия: `payouts.post`, `post_payout`, `post_transfers`, `transfer_initiate`. У ЮKassa
`operationId` отсутствует, и не срабатывали пять правил из шести. Правила переведены на
`method_name`: он собирается из глагола HTTP и пути при отсутствии собственного имени
операции, привязка к началу строки снята.

**Второе: `payment` не является признаком выплаты.** Одно правило давало три очка за любое
из `payout|payment|transfer|order|charge`, поэтому приём платежа и выплата получали
одинаковый счёт: на Stripe роль занимал `post_charges`, на Paystack — `charge_create`.
Существительные разделены:

- `payout|disburse|withdraw|cashout|remit|transfer` — движение денег **от нас**, вес 6;
- `payment|order|batch` — что угодно, вес 2.

**Третье: вето на создание объектов, не являющихся выплатой.** `create_payment_link`,
`create_domestic_payment_consents`, `create_incoming_payment`, `create_webhook_subscription`
занимали роль создания. В вето добавлены `consent`, `incoming`, `link`, `credential`,
`token`, `instrument`, `recipient`, `quote`, `session`, `intent`, `basket`, `permit` и
около десяти других. Список составлен по ошибкам на реальных описаниях: каждому слову
соответствует одна неверная сборка.

**Четвёртое: вето по методу HTTP.** `GET` и `DELETE` сняты с роли создания, `POST` — с
роли статус-запроса. Это устранило несколько ложных срабатываний одновременно.

**Пятое: пороги.** `create_request` повышен с 10 до 13, `fetch_status` и `cancel_request` —
с 8 до 14. Основание: операция создания без слов об исходящем платеже набирает ровно 12
очков, `GET` по идентификатору — ровно 8; таких операций в описаниях десятки.

## Интерпретация результатов

**Правила подобраны по этому же корпусу.** Их результат 82 % получен на выборке, по
которой они настраивались, и прямое сравнение с 83 % у модели, корпус не видевшей,
некорректно. Обоснованная формулировка: под известный набор описаний регулярки доводятся
до уровня модели при нулевой стоимости и времени порядка миллисекунды. Поведение на
описании вне корпуса замер не измеряет; результат на `quantumpay` из первого замера
указывает на снижение.

**Эмбеддинги на реальных описаниях неработоспособны.** 20 неверных сборок из 38 и 4 верных
отказа из 20. Причина следует из устройства способа: косинусовая близость всегда
возвращает ближайшего кандидата, механизма отказа нет, а порог, подобранный на пяти
описаниях, на сорока не применим. Оценка ширины окна порога из первого замера (0.017)
подтвердилась.

**Модель точна по ролям и неточна в отказах.** 83 % верных ролей — лучший результат до
настройки правил; `process_callback` определяется в 30 случаях из 31 против 31 из 41 у
правил. При этом 8 неверных сборок означают назначение роли там, где требуется отказ.
Оговорка: из десяти описаний без ответа девять относятся к группе, требующей отказа, то
есть выборка обрезана именно там, где возможны ошибки этого типа.

**Ролевая точность занижает результат правил.** Большая часть оставшихся ошибок — лишние
`fetch_status` и `process_callback` на описаниях, где `create_request` верно отказал.
Сборка в этих случаях останавливается на обязательной роли, и такие привязки не попадают
в результат. По итоговым сборкам у правил 18 верных, 1 неверная и 21 верный отказ из 21.

## Оставшиеся ошибки правил

- `fire-com`: роль создания заняла `add_bank_transfer_batch_payment` вместо
  `create_batch_payment`. Эталонная разметка здесь неоднозначна: в Fire выплата состоит из
  трёх шагов — создать пачку, добавить в неё платежи, отправить.
- `openbanking-ch`: `initiate_payment` набрал 12 при пороге 13, роль осталась незанятой.
  Порог повышался для отсечения ложных срабатываний; путь здесь шаблонный
  (`/{payment-service}/{payment-product}`), поэтому два очка за путь без параметров не
  начислены.

Обе ошибки связаны с границей отсечения, а не с распознаванием, и устраняются правкой
`base.yml` ценой возврата части ложных срабатываний.

# Настройка до нуля ошибок на корпусе

Правила доведены до полного совпадения с эталонной разметкой. Результат на всех 41
описании:

| способ  | верных сборок | неверных сборок | верных отказов | `create_request` | всего ролей |
| ------- | --------------- | ----------------- | ---------------- | ---------------- | ----------- |
| `rules` | **20/20**       | **0**             | **21/21**        | **41/41**        | 153/164     |

Оставшиеся 11 ролей — лишние `fetch_status`, `process_callback` и `cancel_request` на
описаниях без выплат. Сборка в этих случаях останавливается на обязательной роли, и
привязки в результат не попадают: на 20 описаниях с выплатами счёт **80/80**.

## Изменения сверх первой настройки

Первая настройка дала 63/80 и состояла из изменений состава признаков: чтение
`method_name` вместо `operationId`, разделение слов об исходящем платеже и слова
`payment`, запрет создания выплаты методом `GET`. Оставшиеся 17 ошибок потребовали точечных
правок:

- **Отмена приёма платежа распознавалась как отмена выплаты.** У ЮKassa раздел выплат не
  содержит отмены, но есть `POST /payments/{id}/cancel`. Отсекается условием «в имени есть
  `payment` и нет ни одного слова об исходящем платеже» — регулярка с отрицательным
  просмотром вперёд.
- **Авторизация относится к приёму денег.** Klarna создаёт заказ по пути
  `/payments/v1/authorizations/{token}/order`; вето по `authoris` в пути отсекает это, не
  затрагивая верные операции. Дополнительно выявлено, что `authoriz` не покрывает
  британское написание `authorisation`: из-за этого у швейцарского Open Banking роль
  занимал `start_payment_authorisation`.
- **`initiate` не совпадает с `initiation`.** `initiate_payment` не добирал двух очков,
  роль оставалась незанятой. Шаблон сокращён до `initiat`.
- **Около десяти слов добавлено в вето**: проверка вебхука (`ping`), его отключение
  (`disable`), события биллинга (`meter`, `billing`), терминал (`terminal`), лента событий
  (`timeline`), журнал аудита (`audit`), перечисление позиций (`item`), реквизит
  получателя (`recipient`), карта (`card`), подписка (`subscription`).
- **Одна правка эталонной разметки.** У Fire выплата состоит из трёх шагов: завести пачку,
  добавить в неё платёж, отправить. Верным ответом был записан первый шаг, тогда как
  контракт создаёт одну выплату за раз, чему соответствует второй. Ошибка исправлена в
  `bench/truth.yml`, а не подгонкой правил под неверный эталон.

## Стоимость результата

Словарь распознавания вырос так:

| архетип         | слов в правилах | слов в вето |
| --------------- | --------------- | ----------- |
| `creation`      | 54              | **65**      |
| `status_lookup` | 38              | **39**      |
| `callback`      | 19              | **25**      |
| `cancellation`  | 43              | 19          |

**Около половины словаря описывает не выплату, а признаки её отсутствия.** Этот
негативный словарь составлен по конкретным ошибкам на конкретных сорока описаниях:
`basket` добавлен по швейцарскому Open Banking, `meter` — по Stripe, `ping` — по Velo,
`timeline` — по Rebilly.

Следствие:

**Результат отражает настройку на корпус, а не обобщение.** Правила безошибочны на
выборке, по которой подбирались. Аналогичная ситуация наблюдалась с порогом эмбеддингов:
20 из 20 на пяти описаниях и 14 из 18 при двадцати неверных сборках на сорока одном.
Поведение на следующем описании замер не предсказывает; результат на `quantumpay`
показывает характер возможного отказа — ошибка на непредусмотренном слове.

Границы применимости:

- **Установлено:** под фиксированный набор описаний правила доводятся до безошибочности
  при нулевой стоимости и времени порядка миллисекунды, и превосходят на нём модель
  (16/20 и 8 неверных сборок).
- **Не установлено:** сохранение результата на описании вне корпуса. Замер этого не
  измеряет, пока проверочная и настроечная выборки совпадают.

Для измерения обобщения нужна выборка, отложенная **до** настройки: подбор на части
описаний, измерение на оставшейся части без обращения к ней в процессе. В данном замере
все 41 описание использованы при настройке.

# Проверка на отложенном описании: Dwolla

Предыдущие результаты получены на корпусе настройки и не характеризуют обобщение. Dwolla —
сорок второй провайдер: описание загружено и размечено **после** завершения настройки
правил, в подборе не участвовало, слова словаря под него не добавлялись.

Описание отличается от корпуса настройки: 82 операции, ACH-выплаты в США, лексика
`initiate_transfer`, `funding-sources`, `mass-payments`, `beneficial-owners`. Статус и
отмена находятся на одном пути `/transfers/{id}` и различаются методом.

Разметка проставлена по списку операций до первого прогона:

| роль               | верный ответ        |
| ------------------ | ------------------- |
| `create_request`   | `initiate_transfer` |
| `fetch_status`     | `get_transfer`      |
| `process_callback` | заглушка            |
| `cancel_request`   | `cancel_transfer`   |

## Результат

| способ       | create_request                       | fetch_status   | process_callback         | cancel_request    | итог    |
| ------------ | ------------------------------------ | -------------- | ------------------------ | ----------------- | ------- |
| `rules`      | `initiate_transfer` ✓                | `get_transfer` ✓ | `retry_webhook` ✗      | `cancel_transfer` ✓ | **3/4** |
| `embeddings` | `initiate_mass_payment` ✗            | `get_transfer` ✓ | `get_webhook` ✗        | `cancel_transfer` ✓ | 2/4     |
| `llm`        | не проверен: ключ к прокси умер      | —              | —                        | —                 | —       |

**Правила заняли все три роли, от которых зависит сборка.** Негативный словарь на это не
повлиял: ни одно из 65 вето-слов к верным операциям не применилось. Сработали структурные
изменения первой настройки: чтение `method_name`, отнесение `transfer` к словам об
исходящем платеже, запрет создания выплаты методом `GET`.

**Ошибка возникла в предсказанном месте.** `retry_webhook` — это
`POST /webhooks/{id}/retries`, повтор доставки уведомления. Роль `process_callback` не
различает приём уведомления и управление уведомлениями; на Dwolla это дало одну ошибку из
четырёх. В вето присутствует `resend`, но отсутствует `retry` — разница между верным и
неверным результатом здесь в одном слове, что показывает неустойчивость негативного
словаря.

**Эмбеддинги ошиблись в роли создания:** выбран `initiate_mass_payment` вместо
`initiate_transfer`. Обе операции относятся к выплатам, но контракт создаёт одну выплату
за раз, поэтому собранный сервис обращался бы к неверному эндпоинту.

## Влияние на выводы

Предположение о том, что результат целиком объясняется настройкой на корпус, на одном
отложенном описании **не подтвердилось для трёх ролей из четырёх**. Структурная часть
правок переносится; переносимость негативного словаря замер не проверяет, поскольку здесь
он не применялся.

Ограничение выборки: 3/4 на Dwolla не означает 75 % на произвольном провайдере и не
отменяет того, что 65 вето-слов составлены по сорока одному конкретному описанию. Для
оценки обобщения требуется не менее пяти-шести отложенных описаний, размеченных до
настройки.

Добавление слова `retry` в вето дало бы на Dwolla 4/4, но перевело бы описание из
отложенной проверки в настроечную выборку. Слово не добавлено.

# Отложенная выборка: шесть провайдеров

Выборка расширена до шести описаний: добавлены **Plaid**, **Modern Treasury**, **Lithic**,
**Moov**, **Ripple Payments Direct**. Все загружены и размечены **после** доведения правил
до нуля ошибок на корпусе; слова словаря под них не добавлялись ни до, ни после прогона.

Эталонная разметка составлена вручную по спискам операций до первого прогона — файл
`bench/truth.yml`, группа помечена комментарием.

## Результат

| описание          | операций | правила | что не так                                                              |
| ----------------- | -------- | ------- | ----------------------------------------------------------------------- |
| `ripple-payments` | 23       | **4/4** | —                                                                       |
| `dwolla`          | 82       | 3/4     | `retry_webhook` вместо незанятой роли                                    |
| `moov`            | 136      | 3/4     | `create_transfer_options` вместо `create_transfer`                       |
| `modern-treasury` | 186      | 2/4     | `create_expected_payment` вместо `create_payment_order`                  |
| `lithic`          | 219      | 1/4     | `post_book_transfers` вместо `create_payment`                            |
| `plaid`           | 351      | **0/4** | все четыре роли определены неверно                                       |

**Итого: 13/24 роли (54 %), верных сборок 2 из 6.**

Для сравнения, на корпусе, по которому подбирали: **83/84 роли (99 %), 21 верная сборка из 21.**

Эмбеддинги на тех же описаниях: **5/12 ролей на трёх обработанных описаниях**; остальные
три превысили лимит токенов Voyage. Модель не проверена: ключ к прокси недоступен с
предыдущего прогона.

## Интерпретация

**Результат снизился с 99 % до 54 %.** На выборке из шести описаний предположение
подтвердилось: нулевая ошибка на корпусе объясняется настройкой на корпус.

Ошибки концентрируются в трёх правилах, введённых при настройке:

**Слово `transfer` с весом 6 срабатывает слишком часто.** Оно введено для отделения выплаты
от приёма платежа и на корпусе работало. На отложенной выборке оно перевешивает верный
ответ в трёх случаях: у Plaid побеждает `processor_bank_transfer_create` вместо инициации
платежа, у Lithic — `post_book_transfers` (внутренняя проводка) вместо ACH-платежа, у Moov
— `create_transfer_options` (расчёт доступных способов) вместо перевода.

**Два очка за путь без параметров определяют исход.** У Moov верный `create_transfer`
находится на `/accounts/{accountID}/transfers` — путь с параметром, надбавка не
начисляется. Неверный `create_transfer_options` находится на `/transfer-options`, получает
надбавку и выигрывает этими двумя очками. Правило вводилось как признак создания ресурса в
коллекции, но фактически отдаёт предпочтение верхнеуровневым путям.

**Запрет не-GET для статус-запроса дал 0/4 на Plaid.** Plaid читает данные методом POST:
`POST /payment_initiation/payment/get`. Вето `\A(post|put|patch|delete)\z` вводилось как
структурное ограничение и оказалось неверным.

Отдельный случай: `create_expected_payment` у Modern Treasury — запись об **ожидаемом
входящем** платеже. Вето содержит `incoming`, но не содержит `expected`.

## Вывод

Результаты замера:

- **Структурные правки переносятся.** Чтение `method_name` вместо `operationId` и запрет
  создания выплаты методом `GET` работают на описаниях вне корпуса. Ripple с операцией
  `create_payment_v2` разобран полностью, Dwolla и Moov — на три четверти.
- **Словарь не переносится.** 65 вето-слов, добавленных по одному на ошибку, на новых
  описаниях не применились ни разу; два структурных правила — вес `transfer` и надбавка за
  путь без параметров — ухудшили результат.
- **Результат зависит от размера описания.** 4/4 на 23 операциях, 0/4 на 351. С ростом
  числа однотипных соседних операций вероятность неверного выбора увеличивается.

Вывод для документации: показатель «100 % на корпусе» не характеризует поведение
инструмента; ориентиром служат **54 % ролей на незнакомых описаниях и две верные сборки из
шести**. Характер ошибок при этом остаётся проверяемым: правила выбирали неверную
операцию, и выбор зафиксирован в `mapping.yml`.

По итогам замера правила **не изменялись**: изменение под отложенную выборку лишает её
статуса отложенной.
