> выявила также проблемы генерации и заполнения API-запросов; готовность всего

## Цель и границы

Довести ветку `feat/classifier-recognition` до безопасного слияния: исправить три
подтверждённых дефекта и проверить отсутствие регрессий. Классификатор должен
оставаться детерминированным: регулярки и структурные проверки, без LLM,
embeddings и внешних сервисов. Не расширять корпус провайдеров, не переписывать
архитектуру и не менять массово регулярки ради улучшения процента.

Не сливать в `main`/`deploy` и не запускать деплой без отдельного поручения.

## Задачи

### 1. Сохранить ссылки Swagger 2.0

Файл: `app/service/adapter_builder/parsing/swagger2_normalizer.rb`.

Нормализатор не сохраняет общие `parameters` и `responses`. Ссылки вида
`#/parameters/Payout` и `#/responses/Payout` теряются: разбор проходит без ошибки,
но схема запроса/ответа становится `nil`.

Обеспечить разрешение ссылок и преобразование соответствующих объектов в форму,
которую понимает парсер. Одного копирования секций недостаточно: body-параметр
и response.schema должны пройти нормализацию после раскрытия ссылки.
Учесть параметры уровня пути и операции. Добавить тесты на общие body-параметры,
ответы и параметры пути; сохранить работу встроенных схем и `#/definitions/...`.

### 2. Не связывать разные ресурсы по общему префиксу

Файл: `app/service/adapter_builder/classification/coherence.rb`.

Подтверждённый контрпример: создание перевода
`POST /accounts/{account_id}/transfers` считается связанным с
`GET /accounts/{account_id}`, хотя второе читает счёт, а не перевод.

Уточнить проверку связи создания со статусом и отменой: вложенность адресов сама
по себе не доказывает идентичность ресурса. Не смешивать родителя с дочерним
объектом, пачку с отдельной выплатой и разные платёжные потоки.
При недостаточных доказательствах оставлять роль неназначенной с объяснением.
Добавить отрицательные тесты и положительные тесты для обычных REST-адресов
и RPC-вариантов, например `/payments/create` и `/payments/get`.

### 3. Связать callback с выбранным потоком выплаты

Файл: `app/service/adapter_builder/classification/classifier.rb`, метод `choose`.

Сейчас для callback выбирается первый подходящий кандидат без связи с созданием.
На локальном TrueLayer выбирается `webhook_payment_links`, хотя ожидается
`webhook_payouts`.

Учитывать доступные доказательства принадлежности события выбранному потоку.
Не переносить механически проверку REST-путей на именованные webhooks.
Не назначать уведомления о приёме платежей или карточной авторизации выплатам.
При неоднозначности предпочитать обоснованный отказ. Сохранить корректные случаи
из `paths`, OpenAPI `webhooks` и вложенных `callbacks`; добавить тесты с несколькими
конкурирующими событиями. Не вводить исключения по именам провайдеров.

## Проверки и исходная точка

Аудит выполнен на `7ddb793`. Повторный локальный замер дал:

| Метрика | Результат |
| --- | --- |
| Прочитано описаний | 71/71 |
| create_request | 65/71 |
| fetch_status | 61/71 |
| process_callback | 65/71 |
| cancel_request | 65/71 |

Числа включают правильные отказы. Это не точность только на API выплат.
У GOV.UK Pay остаётся ложное назначение выплаты; отслеживать его отдельно,
не объявлять продуктовой неоднозначностью. Группа `holdout` уже использовалась
при настройке и не является независимой проверкой обобщения.

1. До правок повторить доступные тесты и замер, зафиксировать исходные ошибки.
2. Для каждого дефекта добавить небольшой воспроизводимый тест в отслеживаемую
   Git директорию `spec/`, затем исправить код и прогнать точечные тесты.
3. В конце выполнить полный RSpec и замер обоих корпусов; сравнить назначения
   по каждому провайдеру, а не только суммарные проценты. Отдельно показать ложные
   назначения, пропуски и выбор неправильной операции.
4. Не менять эталонную разметку под результат алгоритма. Если эталон спорный,
   описать доказательства и вынести вопрос отдельно.
5. Итоговый отчёт: изменения, команды и результаты проверок, сравнение до/после,
   оставшиеся ограничения и рекомендация по слиянию. Не заявлять, что успешный
   разбор или unit-тесты доказывают работоспособность реальной интеграции.

Пример локальных команд (выбрать доступный Ruby/Bundler, здесь Ruby 3.3.12):

```sh
LANG=en_US.UTF-8 BUNDLE_WITHOUT=classifiers bundle exec rspec
LANG=en_US.UTF-8 BUNDLE_WITHOUT=classifiers bundle exec ruby bench/measure.rb bench/truth.yml bench/truth-new.yml
```

В предыдущем отчёте заявлены 303 теста без ошибок; аудит их повторно не запускал,
поэтому результат нужно проверить заново.

`bench/` игнорируется Git: корпус, разметка и `measure.rb` могут отсутствовать
в свежем клоне. Не добавлять весь каталог в Git. Обязательные регрессионные тесты
с минимальными синтетическими примерами должны работать без него. Если локального
корпуса нет, явно отметить, что сравнение 71 описания не выполнено.

## Критерий готовности

Три контрпримера покрыты тестами и исправлены; полный набор тестов проходит;
нет новых необъяснённых ошибочных назначений на доступном корпусе. Любое падение
показателя разобрано явно (безопасный отказ вместо чужой операции не скрывать
за общей суммой). При оставшихся существенных проблемах не рекомендовать слияние
всей ветки, а отдельно оценить готовность исправлений парсера.
