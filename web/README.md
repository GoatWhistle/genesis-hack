# Витрина RSOCKET

Сайт, который показывает, как инструмент разбирает чужое описание API и что из
этого получается: операции разбегаются по ролям со счётом и порогом, статусы
переводятся в состояния контракта, а каждая строка собранного сервиса помнит
решение, из которого выросла.

Это **отдельная от решения часть**. На решение кейса она не влияет, ни один
Ruby-файл от неё не зависит, и вся она умещается в каталоге `web/`.

Стек: React 19, TypeScript, Vite, Tailwind (только как база, вёрстка на
именованных классах), shiki для подсветки. Роутер свой, библиотеки нет.

## Запуск

    pnpm install
    pnpm dev

Открывается на `http://localhost:5173`.

Сайт работает без бэкенда: все разборы запечены в сборку. Бэкенд нужен только
для живого режима на `/lab` — поднимается из корня репозитория:

    docker compose up -d
    curl http://127.0.0.1:9292/health

В разработке `/api/*` проксируется Vite на `127.0.0.1:9292`. В проде тот же
путь отдаёт Caddy с того же домена, поэтому код клиента одинаков и там, и там.

## Страницы

| Путь | Что там |
|---|---|
| `/` | Сцена раздачи ролей на настоящем прогоне novapay с перемоткой и повтором; табло «одна сумма — четыре разных числа в теле запроса» с ползунком; проверка регулярки прямо на странице; два слоя правил (`base.yml` ↔ `contract.yml`); один вход — два выхода (`NovapayService` и `NovapayClient`); честные `warnings` с nordbank; три способа запустить |
| `/lab` | Ядро сайта. Схема из шести стадий сборки, затем пять шагов разбора: разбор описания, раздача ролей со счётом и порогом, статусы, сумма с ограничениями и авторизацией, код. В шаге «Код» наведение связывает строку с решением, которое её породило, и наоборот. Выбор провайдера и контракта, история недавних разборов, живой режим со своим описанием, скачивание архива |
| `/rules` | Настоящий `base.yml` инструмента, разобранный по смыслу: архетипы операций с правилами и veto, словари распознавания, профили контрактов. Проверка регулярки на своём `operationId` и песочница: правишь вес или регулярку — видно раздачу ролей до и после на всех четырёх провайдерах |
| `/providers` | Четыре описания рядом: где они расходятся (имя операции создания, единицы суммы, авторизация, статусы, уведомления), и разбор каждого целиком — отчёт, собранные файлы, `INTEGRATION.md` рендером, архив |
| `/docs` | Документация инструмента: воспроизводимая запись вывода CLI, HTTP API с кнопкой «выполнить» в живом режиме, хранилища, как добавить контракт, как добавить правило, разбор частых вопросов |

Состояние страниц живёт в адресе (`?provider=`, `?contract=`, `?r=`), поэтому
ссылкой можно поделиться на конкретный разбор.

## Данные

Два источника, режим всегда видно.

**Запечённые прогоны.** `src/data/runs/` — восемь дословных ответов
`POST /build`: четыре провайдера (`kassabox`, `nordbank`, `novapay`,
`swiftpay`) × два контракта (`space_payments`, `plain_client`), плюс профили
контрактов и содержимое хранилища правил. Не выдуманные фикстуры: их пишет
`pnpm bake`, гоняя настоящий сервис по описаниям из `examples/`. Показ не
сломается из-за упавшего сервера.

Перезапечь после изменений в решении:

    docker compose up -d
    cd web && pnpm bake

**Живой режим.** На `/lab` можно вставить своё описание — оно уходит в
настоящий `POST /api/build`, ответ показывается тем же разбором. Если сервис
недоступен, страница честно об этом говорит и предлагает вернуться к
запечённому режиму.

## Где что лежит

    src/layout/      каркас: App, шапка, подвал, роутер, список маршрутов
    src/screens/     по каталогу на страницу, внутри ui/ и model/
    src/shared/      общее: api, model, ui, lib, design
    src/data/runs/   запечённые прогоны
    scripts/         запекание, smoke-проверка, запрет комментариев
    infra/           Caddyfile, compose для прода, инструкция по выкладке

Подробно — [ARCHITECTURE.md](ARCHITECTURE.md): раскладка каталогов, правила,
обязательные при правке кода, и дизайн-система. Выкладка на VPS —
[infra/DEPLOY.md](infra/DEPLOY.md).

## Команды

    pnpm dev         разработка на 5173
    pnpm typecheck   tsc --noEmit
    pnpm lint        запрет комментариев + eslint
    pnpm build       typecheck + сборка в dist/
    pnpm smoke       проверка собранного dist/ и запечённых прогонов
    pnpm preview     просмотр собранного dist/
    pnpm bake        перезапекание прогонов с живого сервиса

Полная проверка перед сдачей — четыре команды подряд, `smoke` требует уже
собранного `dist/`:

    pnpm typecheck && pnpm lint && pnpm build && pnpm smoke
