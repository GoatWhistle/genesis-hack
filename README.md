# RSOCKET

Инструмент, который читает описание API платёжного провайдера в формате OpenAPI и
собирает по нему интеграцию: сервис на Ruby по контракту заказчика, инструкцию по
подключению, примеры запросов и ответов и отчёт о том, как он это описание понял.

Смысл в том, чтобы не писать руками одно и то же для каждого нового провайдера.
Инструмент сам разбирается, какой метод создаёт выплату, какие состояния означают
успех, какие ошибки можно повторять, в чём передаётся сумма, — и честно говорит, в чём
он не уверен, вместо того чтобы молча угадать.

## Что получается на выходе

Одна сборка — четыре файла в `output/<провайдер>/`:

| Файл                     | Что в нём                                                            |
| ------------------------ | -------------------------------------------------------------------- |
| `<провайдер>_service.rb` | сервис по контракту заказчика: запросы, статусы, ошибки, webhook     |
| `INTEGRATION.md`         | инструкция: настройка, авторизация, методы, маппинг статусов, ошибки |
| `fixtures.json`          | примеры запросов, ответов по кодам и входящих уведомлений            |
| `mapping.yml`            | что инструмент понял: роли, счёт, сработавшие правила, единицы суммы |

`mapping.yml` — главный файл для проверки глазами.

## Установка

Нужен Ruby 3.3.12 — версия записана в `.ruby-version`.

```
brew install ruby@3.3
export PATH="/opt/homebrew/opt/ruby@3.3/bin:$PATH"
```

С rbenv версия подхватится из `.ruby-version` сама: `rbenv install 3.3.12`.

Дальше — гемы:

```
gem install bundler
bundle install
```

Зависимостей немного и все опенсорсные: `thor` для командной строки, `rack`/`rackup`/
`webrick` для HTTP-режима, `rspec`, `rubocop` и `webmock` для проверок.

## Короткие команды

Всё, что описано ниже, продублировано в `Makefile` — `make help` печатает список:

| Команда                     | Что делает                                              |
| --------------------------- | ------------------------------------------------------- |
| `make install`              | поставить гемы                                          |
| `make check`                | тесты и линтер разом                                    |
| `make build PROVIDER=novapay` | собрать интеграцию по `examples/<провайдер>/`         |
| `make examples`             | собрать все четыре примера                              |
| `make serve PORT=8080`      | поднять HTTP-сервер локально, без S3                    |
| `make request`              | отправить описание на поднятый сервер и разложить ответ |
| `make up`, `make down`      | стек в контейнерах: MinIO и сервер                      |
| `make clean`                | вычистить `output/`                                     |

Переменные `PROVIDER`, `SPEC`, `CONTRACT`, `OUT`, `HOST`, `PORT`, `STORAGE` перекрываются
в командной строке: `make build PROVIDER=kassabox CONTRACT=plain_client`.

## Проверка, что всё поднялось

```
bundle exec rspec      # 221 пример: разбор, классификация, печать, HTTP, сгенерированный сервис
bundle exec rubocop    # линтер
```

Тесты не только проверяют внутренности: `spec/integration/generated_service_spec.rb`
собирает сервис, грузит его как обычный файл и смотрит через `webmock`, какой запрос
уходит на провод.

Какие правила видит инструмент прямо сейчас:

```
bundle exec bin/rsocket doctor
```

```
контракт: space_payments — контракт Space Payments (Provider::BaseService)
правила:  локальный каталог <репозиторий>/app/config/rules
  create_request     порог 10, обязательна,    правил: 5, calls_provider creates_operation
  fetch_status       порог  8, обязательна,    правил: 4, calls_provider
  process_callback   порог  8, необязательна,  правил: 4, receives_callback
  cancel_request     порог  8, необязательна,  правил: 4, calls_provider
```

## Два способа запуска

Сборка доступна двумя путями. Они ведут в один и тот же менеджер сборок, поэтому на
одном описании дают одинаковые файлы — отличается только то, откуда приходит описание и
куда уходит результат.

|                     | Командная строка                          | HTTP-сервер                                              |
| ------------------- | ----------------------------------------- | -------------------------------------------------------- |
| команда             | `bin/rsocket build`                       | `bin/rsocket serve`, дальше `POST /build`                |
| откуда описание     | файл на диске                             | тело запроса                                             |
| откуда правила      | `app/config/rules/`                       | те же файлы или бакет S3                                 |
| куда результат      | файлы в `output/<провайдер>/`             | JSON с содержимым файлов, плюс они же на диске или в S3  |
| когда удобнее       | собрать интеграцию руками, прочесть отчёт | встроить в чужой пайплайн, править правила на ходу       |

Обоим режимам, кроме репозитория, ничего не нужно: S3 включается по желанию.

## Запуск: командная строка

```
bundle exec bin/rsocket build --spec examples/novapay/provider_api.yaml --provider novapay
```

```
контракт: space_payments
  create_request     POST /payouts
  fetch_status       GET /payouts/{payout_id}
  process_callback   POST /webhooks/payout
  cancel_request     POST /payouts/{payout_id}/cancel
  ! сумма провайдера: amount (integer), единицы: копейки
  ! подпись приходит в заголовке X-NovaPay-Signature

  output/novapay/novapay_service.rb
  output/novapay/INTEGRATION.md
  output/novapay/fixtures.json
  output/novapay/mapping.yml
```

Сначала — какой эндпоинт какой роли достался, потом строки с `!`: решения, которые
стоит проверить глазами, и всё, что инструмент не поддержал. Роль, под которую ничего
не нашлось, печатается как `заглушка`, и в сгенерированном сервисе на её месте будет
честный отказ, а не выдумка. Если не нашлись обязательные роли, сборка останавливается
и говорит, каких именно не хватило.

Флаги:

| Флаг               | Что задаёт                                                       | По умолчанию     |
| ------------------ | ---------------------------------------------------------------- | ---------------- |
| `-s`, `--spec`     | путь к описанию OpenAPI (YAML или JSON)                          | обязателен       |
| `-p`, `--provider` | имя провайдера: из него имя класса, файла и переменных окружения | обязателен       |
| `-o`, `--out`      | каталог результата                                               | `output`         |
| `-c`, `--contract` | профиль контракта, под который собираем                          | `space_payments` |
| `--storage`        | откуда правила и куда результат: `local` или `s3`                | `local`          |

`--provider novapay` даёт класс `Provider::NovapayService`, файл `novapay_service.rb` и
переменные `NOVAPAY_BASE_URL`, `NOVAPAY_API_KEY`, `NOVAPAY_CALLBACK_SECRET`.

## Что инструмент умеет разбирать

В `examples/` лежат четыре описания, специально написанные непохожими друг на друга:
разные имена операций, разная вложенность полей, разные единицы суммы и способы
авторизации. Собираются все:

```
for p in novapay kassabox nordbank swiftpay; do
  bundle exec bin/rsocket build -s examples/$p/provider_api.yaml -p $p
done
```

| Пример     | Чем отличается                                                                                                                          |
| ---------- | --------------------------------------------------------------------------------------------------------------------------------------- |
| `novapay`  | СБП-выплаты, сумма в копейках, ключ в заголовке, webhook с HMAC-подписью                                                                |
| `kassabox` | конверт `data.*` в ответе, поля `orderNo`/`sum.value`/`payee.cardToken`, свой заголовок идемпотентности, две схемы авторизации на выбор |
| `nordbank` | сумма строкой в рублях, `oneOf` в реквизитах получателя, состояния капсом, `securitySchemes` вообще нет                                 |
| `swiftpay` | сумма числом в рублях, Bearer-токен, webhook не описан — статус узнаётся опросом                                                        |

Чего в описании нет, то и не выдумывается: у `nordbank` метод `authorize` собирается с
TODO и объяснением, у `swiftpay` `process_callback` возвращает отказ
`callback_not_supported`. Всё такое попадает в строки с `!` и в `mapping.yml`.

## Под какой контракт собираем

Контракт заказчика — это профиль правил, а не код инструмента. Профилей может быть
сколько угодно:

```
bundle exec bin/rsocket contracts
```

```
  plain_client     обычный клиент на исключениях
* space_payments   контракт Space Payments (Provider::BaseService)
```

```
bundle exec bin/rsocket build -s examples/swiftpay/provider_api.yaml -p swiftpay \
                              --contract plain_client
```

По тому же описанию получится другой класс с другими именами методов
(`send_payout`, `payout_state`, `read_callback`) и другой обработкой ошибок — потому что
это задаёт профиль, а не разбор.

## Как это устроено

Разбор чужого API и знание о контракте заказчика разведены намеренно: в правилах
разбора нет ни одного имени метода заказчика, а в профиле контракта — ни одного имени
провайдера.

| Что                     | Где                                           | Зачем                                                                                 |
| ----------------------- | --------------------------------------------- | ------------------------------------------------------------------------------------- |
| правила разбора         | `app/config/rules/base.yml`                   | как разные провайдеры называют одни и те же операции, состояния, ошибки и поля        |
| профили контрактов      | `app/config/rules/contracts/<профиль>/`       | `contract.yml` — роли, статусы, коды ошибок; рядом ERB-шаблоны выходных файлов        |
| разбор описания         | `app/service/adapter_builder/parsing/`        | чтение OpenAPI, раскрытие `$ref`, вытаскивание схем и примеров                        |
| распознавание ролей     | `app/service/adapter_builder/classification/` | какая операция за что отвечает, со счётом и порогом                                   |
| решения о сборке        | `app/service/adapter_builder/analysis/`       | статусы, ошибки, тело запроса, единицы суммы, подпись webhook, предпроверки, фикстуры |
| печать файлов           | `app/service/adapter_builder/rendering/`      | ERB-шаблоны профиля и отчёт                                                           |
| командная строка и HTTP | `app/controller/`                             | тонкие слои над одним и тем же менеджером сборок                                      |
| адаптеры и хранилища    | `app/adapter/`, `app/repositories/`           | чтение описания, запись результата, диск или S3                                       |

Роль назначается по правилам со взвешенным счётом и порогом: слабый признак (`POST`) не
перевешивает сильный (глагол в начале `operationId`), а veto снимает кандидата целиком —
иначе `cancelPayout` выигрывал бы роль создания. Счёт, порог и сработавшие правила по
каждой роли лежат в `mapping.yml`.

Чтобы инструмент начал понимать ещё одно написание `operationId` или ещё одно название
статуса, правится одна строка в `base.yml` — сразу для всех контрактов и провайдеров.
Чтобы собрать под другой интерфейс, добавляется профиль в `contracts/` — код инструмента
не меняется.

## Запуск: HTTP-сервер

### Поднять

```
bundle exec bin/rsocket serve --storage local
```

```
rsocket слушает http://127.0.0.1:9292
  GET  /             — что умеет сервис
  GET  /health       — жив ли он
  GET  /openapi.yaml — описание этого API
  GET  /contracts    — профили контрактов и их роли
  GET  /rules        — что лежит в хранилище правил
  PUT  /rules/<ключ> — записать правила или шаблон
  POST /build        — сборка: ?provider=имя[&contract=профиль], тело — описание
хранилище: local: правила — локальный каталог <репозиторий>/app/config/rules, результат — каталог output
```

`--storage local` здесь обязателен: серверу, в отличие от командной строки, по умолчанию
подставляется S3, и без настроенного бакета он не поднимется — но скажет, каких
переменных не хватает, а не упадёт на первом запросе:

```
не поднялось: для хранилища s3 не заданы: RSOCKET_S3_ENDPOINT, RSOCKET_S3_BUCKET,
RSOCKET_S3_ACCESS_KEY_ID, RSOCKET_S3_SECRET_ACCESS_KEY. Либо задайте их, либо выберите local
```

Порт и адрес — флагами `--port` и `--host`. По умолчанию сервер слушает только
localhost: аутентификации у него нет, наружу его выставлять не надо.

### Собрать

Имя провайдера — в строке запроса, описание — телом. `Content-Type` не важен: JSON
узнаётся по первому символу, всё остальное читается как YAML.

```
curl -X POST "http://127.0.0.1:9292/build?provider=novapay" \
     --data-binary @examples/novapay/provider_api.yaml
```

```json
{
  "provider": "novapay",
  "contract": "space_payments",
  "warnings": ["сумма провайдера: amount (integer), единицы: копейки", "..."],
  "locations": ["output/novapay/novapay_service.rb", "..."],
  "files": { "novapay_service.rb": "# frozen_string_literal: true\n...", "...": "..." },
  "report": { "roles": { "create_request": { "endpoint": "POST /payouts", "score": 15 } } }
}
```

`warnings` — те же строки с `!`, что печатает командная строка; `report` — то же, что
уходит в `mapping.yml`; `files` — содержимое каждого файла строкой. Разложить их по
файлам:

```
curl -s -X POST "http://127.0.0.1:9292/build?provider=novapay" \
     --data-binary @examples/novapay/provider_api.yaml \
| ruby -rjson -e 'JSON.parse($stdin.read)["files"].each { |name, body|
    File.write(name, body); puts name }'
```

Ошибки приходят JSON-ом с полем `error`: **400** — запрос сформулирован неверно (нет
`provider`, пустое или неразобранное тело), **422** — описание понято, но для сборки не
годится, и тогда текст называет роли, которых не хватило.

### Через rackup

`config.ru` лежит в корне, так что подойдёт любой сервер приложений:

```
RSOCKET_STORAGE=local bundle exec rackup            # тот же сервис на 9292
RSOCKET_STORAGE=local bundle exec rackup -p 8080
```

### В контейнере

```
docker compose up --build      # MinIO + сервер на localhost:9292
docker compose down
```

Стек поднимает MinIO как S3-хранилище, переносит в бакет правила командой
`bin/rsocket push` и запускает сервер. Разовая сборка тем же образом, без сервера:

```
docker compose run --rm rsocket \
  bundle exec bin/rsocket build -s examples/novapay/provider_api.yaml -p novapay
```

### Настройка

| Переменная                 | По умолчанию                     | Что задаёт                     |
| -------------------------- | -------------------------------- | ------------------------------ |
| `RSOCKET_HOST`             | `127.0.0.1`                      | адрес, который слушает сервер  |
| `RSOCKET_PORT`             | `9292`                           | порт                           |
| `RSOCKET_STORAGE`          | `local` для CLI, `s3` для сервера | хранилище правил и результата  |
| `RSOCKET_CONTRACT`         | `space_payments`                 | профиль контракта по умолчанию |
| `RSOCKET_OUTPUT`           | `output`                         | каталог результата             |
| `RSOCKET_S3_*`             | —                                | endpoint, бакет и ключи S3     |

Полный список ручек, кодов ошибок и переменных — в [docs/http-api.md](docs/http-api.md);
там же про работу через S3 и правку правил на ходу через `PUT /rules/<ключ>`.
Машиночитаемое описание — [docs/openapi.yaml](docs/openapi.yaml), сервис отдаёт его и сам
ручкой `GET /openapi.yaml`.
